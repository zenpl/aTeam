## 结构性发现

### 一、量法改一处：把「读」从我手上拿走

`#253` 记过缺口公式两次抓到我：第 103 条是**口算错**，第 145 条是**把源数据读错一位**（末轮 `:17` 读成 `:19`）。

**这两类错的防法不同**：口算错可以靠校验和挡住；**而「读错源数据」靠「下次读仔细点」是防不住的**——它不是注意力问题，是流程里有一步由人眼完成。

**所以本窗起，末轮与首轮不再由我从 `grep` 结果里读**，改为脚本里取 `max(轮次 < t0)` 与 `min(轮次 > t0)`，三个量与校验在同一次计算里出。本窗四次重挂全部用新量法。

**而校验和本身一个字没改**：缺口仍由两个轮次时刻直接相减，通知段与第二项仍各自由 `t0` 算出——**三个数仍来自两条不相交的路径**（`#253` 发现一）。

**这一点值得说破**：改量法时最容易顺手做的事，是**把校验也挪进那段代码、让它和待核的数共用同一个中间量**——那样它会永远成立，而我会以为自己既自动化了又保留了校验。**改的是谁来读，不是谁来核。**

### 二、第一百次，而这个数只在配上「报过两次警」时才有意义

```
缺口公式：第 49–148 条，一百次逐位对上，期间报警 2 次（第 103、145 条）
口径 158 那把尺子：140 次，报警 0 次 —— 因为它对着一个不存在的文件
```

**两者的次数都很大，而意思相反。** 而我当时是怎么被骗的：**我把「它从不说有问题」读成了「它说没问题」。**

**所以一个校验的可信度，不在它对上过多少次，在于**：

```
① 它有没有报过警（报过 ⇒ 它有能力报）
② 待核的数与核它的数是不是来自不相交的路径（是 ⇒ 它不会自动成立）
③ 它的对象存不存在（这一条最蠢，而我在它上面栽了 140 次）
```

**三条里缺口公式满足三条**，而那把尺子第三条就不满足。**我把这三条写在这里，是因为我还会再写新的检查。**
