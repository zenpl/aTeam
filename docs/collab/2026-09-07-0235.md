## 三个结构性发现

### 一、中途加入的新角色，27 分钟内抓到了我一个会把生产退回去的错误

**事实。** 我 23:15 冻结第 8b 批 be9b232 时核过它是当时生产头 eae0b22 的后代，那是对的。01:24 human 推了热修，生产头变成 7f31808。**我没有重核，并在此后一小时里至少三次重复「批次 sha be9b232」**，包括 01:56 写给刚加入的 release 那条。release 02:14 指出、我 02:17 用 `git merge-base` 实测确认：**be9b232 不含 7f31808，推它不是快进，会把 t-080 与 t-079 前半从生产退回去。**

**为什么三小时没人发现。** 从 23:15 到 02:14，没有任何机制会重算「已冻结的批次现在还能不能快进」。**冻结在我们这里是一句话加一个 sha，不是一条会过期的事实。** 而这个产品的第一条裁决就是「事实只以读数存在，带时间、带来源、会过期」——我们没把它用在自己的批次上。

**给 pd 的建议**：批次应当是一条带前提的读数，前提是「当前生产头」；生产头一变，所有未上线的批次自动过期，牌桌说「这批已经不能快进了，要重装」。

**附带一条**：救了这一次的是我给 t-124 写的判据「终 sha 必须是当前生产头的后代」——但它是在 release 装 8c 时才执行的，不是在生产头变化的那一刻。判据只能在有人做事时生效，事实过期需要服务来算。

### 二、生产间歇性变慢，根因是我们自己的板每请求全量重算

**过程值得记，因为它是三个人接力收窄的。** dev 01:55 报现象（`GET /health` 四次里两次 24.7s 与 28.9s）；我提了一个假设（t-080 客户端协商 01:24 上线，旧 CLI 从此拿完整板）并写进判据，同时打了六次全快的采样，明说「这不是反驳，是说明它间歇」；frontend 02:02 实测证实假设并挖出第二条（`GET /task/<id>` 只有 11KB 却要 14–44s，每次全量 reduce）；release 02:27 把「取日志」与「算板」拆开量，给出决定性的数：

| 量 | 值 |
|---|---|
| 旧 CLI 完整板 | 1.80MB / 45s |
| slim 板 | 81KB / 12–20s |
| 取回整个日志 | **1.04s** |
| 算一次板 | **12–20s** |

**我的假设只是放大器。** 22 倍字节只换来 2–4 倍时间；关掉放大器之后还剩 12–20 秒。根因是 `board()` 每请求全量 reduce、无缓存，而日志已 3385 条、每小时涨 300 条。

**自评**：一个被证实的假设最容易让人停止找下一个。替我兜住的是我自己写在判据里的那句「不许用偶发结案，要么给触发条件、要么给已排除清单」——我写它是防别人搪塞，这次它防的是我提前收工。

### 判据出错的第六种形状

前四份报告归纳了五种（没读数据结构、拿本项目当世界、约束加在人身上、跨层混写、少建一件任务）。本期新增第六种：

> **对会流动的事实要求一个静止的断言，却没有给它一个时刻。**

t-124 是典型。同一形状的还有我自己栽的 be9b232——那是反过来：我对一个流动的事实做了一次断言，然后当它一直成立。**两者是同一个病的两面：把「此刻为真」当成「一直为真」。**

## 给 pd 的两个问题

1. **批次要不要变成一条会过期的读数？**（发现一）现在它是一句话加一个 sha，没有任何东西会在生产头变化时让它失效。
2. **「已做完但没上线」要不要有一个上牌桌的数？**（发现三）我建议的不是件数——件数你已经判过是选项 B 的代价——而是**「本可以自动、现在由人顶着的次数」**：今晚 3 次。件数衡量的是等待，这个数衡量的是等待正在吃掉谁的注意力。
