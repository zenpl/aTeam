## 三个结构性发现

### 一、堵洞的检查本身是假的

qa 用 git 实测发现：t-067 的接缝放行检查只匹配证据里有没有某个 sha 字符串，**不验证分支真的包含它**。dev 那条线从没合过 c3cfeee/90af52b，检查照样放行。

这直接推翻了我 21:32 的一个判断——我当时说「自动放行时证据里那个 sha 是唯一保障」，并据此把警告升级为拒绝。那个保障是纸糊的，我的收严建立在假检查上。dev 随后自承四条 done 证据的包含声明不实。

处置：t-074 改用真判定并与 t-073 共用一处实现；pd 定下证据不实的两条路径（判据仍满足→发更正 note；验收靠了不实证据→非作者在同表面推翻，fail 覆盖 pass，不改历史）；t-076 实现推翻路径，qa 用逐字节比对证明 0 条历史事件被改。

**对需求的含义。** T5「互相挡住对方的错误」在本期被验证到了第二层：不只挡住彼此的错误，还挡住「用来挡错的机制本身的错误」。

### 二、同一个病会换楼层，除非从契约上根治

「说没有其实有」修了三轮：第一轮修 overlap 的半截句、第二轮修 touches 的假占位符、第三轮才发现根因是**数据侧把「被瘦身省略」和「本来就没有」发成同一形态**，渲染层根本区分不了。

修完契约后 qa 又发现：`omitted` 是手写数组，与真正裁剪的代码无关，漏一个字段测试照样绿——**根因从渲染层搬到了契约层**。最终改为由裁剪前后比对算出，并用不认字段名的递归断言测试。

由此得到一条可推广的原则，已记入日志：**描述某物的清单若与该物分开手工维护，必然漂移；要由它描述的东西算出来，不要声明。** 按这条自查，今天还有三处同类风险：说明书的职责清单、pd 的 overfit 清单、我的判据模板——第三处今天已经漂了，五次判据被回问就是证据。

### 三、验收开始检查「修复有没有把另一头搞坏」

qa 在 `omitted` 改必填后，主动去查这个改动可能引入的反向错误（完整任务被渲染成一堆「详见 task show」的指路句），实测 0 次。没有人要求它查这个。

三轮 t-075 每一轮都在修「说没有其实有」，很容易滑向反面变成「什么都说详见别处」。这类反向错误不会被原判据发现，因为原判据只问「要求的效果达到没有」。

已写入我的判据模板试用（不建任务）：修复类任务需说明它可能引入的反向错误，并给出该错误未发生的证据。
