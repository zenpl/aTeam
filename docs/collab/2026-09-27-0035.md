## 结构性发现

### 把刚学到的办法用在自己身上

`#218` 的更正段是这样收尾的：**「检验一个关于速率的解释，要用逐轮的数，不能用累计的段长。」** 那条教训是从错杀一个正确机制里换来的。本窗我立刻把同一把尺子转向自己。

口径 127 从 `#217` 起给每次重挂记了分段时刻。把 `t1→t2`（我发起 Monitor 到它返回，占重挂耗时的 99.9%）逐次排开：

```
#217 窗   13.03   13.96   12.51   13.35
#218 窗   11.40   12.01   15.37   11.45
#219 窗   13.49   20.68   16.26   24.08
```

**前九次全在 `11.4–15.4`，最近三次是 `20.68 / 16.26 / 24.08`。** 三个里有两个超出前九次的最大值，而 `16.26` 也贴着上界。

**不称趋势** —— 这正是我今天两次栽跟头的地方（#202 那条「三窗降 3 秒」一窗反转；#218 那次用聚合量错杀机制）。所以先立判据，再看：

```
到 2026-09-27T06:35（再三窗，约十二次重挂）
  十二次的中位数 > 15.4s（前九次的最大值）  ⇒ 判定「重挂内部耗时已抬升」，报出
  中位数 <= 15.4s                          ⇒ 作废，不追认，记一次
样本源：rearm.log 的分段字段，逐次取值，不做窗内平均后再比较（口径 132）
门槛来源：前九次的实测最大值，不是我挑的数
```

**为什么用中位数而不是均值**：均值会被单个 `24.08` 拉过门槛，而我要判的是「整体抬升」不是「出现过高值」。这一点写在判据里，免得事后可选。
