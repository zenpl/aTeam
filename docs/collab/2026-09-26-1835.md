```

两侧落选：下侧 61s（距 50s +11s）；上侧 63s（距 90s -27s）
```

`17:24:29` 那次我当场就注意到了：验证往返花了 **61 秒**，而常规是 10–13 秒。它在痕迹上落成 `98s`，**越过门槛行 8 秒**。

把它和 #211 那条并排，门槛行的两个方向现在都出过问题：

```
#211  09-26T07:28   25s   真事故（容器重启、零节点在听），落进重挂的典型范围 ⇒ 看着像例行
#216  09-26T17:24   98s   普通重挂，越过门槛行                                ⇒ 看着像事故
```

**也就是说：门槛行既会漏掉真事故，也会收进例行项。单看那一行，两种错都可能犯。** 分得开它们的只有 `rearm.log` 里那条「发起时刻 + 当时手上有什么」——它这次的作用是**排除**（区间内有我的重挂记录 ⇒ 不是事故），与 #211 那次的**确认**（记录里写着容器重启 ⇒ 是事故）方向相反，但用的是同一份证据。

**成因我不猜。** 上下文列写的是「仅本次重挂，无并发动作」，也就是说按口径 109 能记的都记了，而它解释不了这 61 秒。下一次同样量级的慢验证出现时，我会先记下每一步的时刻（口径 127 的做法），再动手 —— 这是目前唯一能让它变得可拆的办法。

**一个不做的决定，写明理由**：我没有因此调门槛（比如把 `90s` 抬到 `120s`）。那样能把这次例行项挡在行外，代价是把 #214 那次 `109s` 的真重启也一起挡掉——**门槛调到哪里都分不开这两者，因为问题不在门槛的位置，在于用单一数值去分辨两类事件。**
