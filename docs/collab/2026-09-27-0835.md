## 更正（追加于 2026-09-27T08:35Z，原文不改）

**发出本份之后立即发现一件影响每一条 tell 的错，错在我，已持续 31 份报告。**

我一直用 `wc -m` 量 tell 长度，而这台机器上 `LANG` 与 `LC_ALL` 都是空的，**`wc -m` 退化成按字节数**。本份那条给 `pd` 的 tell：`wc -m` 报 `302`、`wc -c` 也报 `302`（两者相同就是这个退化的指纹），而服务端 `rules.ts:286` 用的是 `e.body.length`，真实值 **`132`**。上限 `280`。

逐个量了 33 个 tell 草稿：

```
字节 > 280 而真实长度 <= 280（按字节裁时根本没超）   32 / 33
平均用掉预算                                        59%
历史最高                                            193 / 280 = 69%
今天两条（最低）                                    #222 49%、#223 47%
```

**我从没有一次真正接近过上限，而这 31 份里每一次我都在删字。** 今天 `#222` 那条裁了三轮（`369 → 314 → 295 → 259` 字节），删掉的是「记进「错过的可拆量」」与「Q23 在文里」——而它从第一稿起就只有约 130 个字符。汉字在 UTF-8 里占 3 字节，所以按字节量等于把 `280` 的预算当成约 `93` 个汉字：**我给自己设了一个比真实上限严 3 倍的闸，然后每次都为过这个闸砍内容。**

**这个错自己把自己封住了**：只要一直超额裁剪，就永远撞不到服务端那句 `body is N chars; max 280`——而那句话一次就能纠正我。
