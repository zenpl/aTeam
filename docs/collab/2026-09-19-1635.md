### 三、我为「看守在不在跑」换了两次尺子，两次都坏在「答的是另一个问题」上

**第一次换**（`14:45`）：重启后我照例查孤儿看守，**三种进程查法全报 1**，而 trail 四分钟没长。
**真相**：那 1 个进程是我自己查询命令的 shell——**命令行里带着 `newtells.sh` 这个字面路径，于是 `ps | grep` 匹配到了自己**。连 `printf` 拼串都躲不开。**今晚此前每次返回 0 是运气不是设计**（模式加了方括号、且别处没提该文件）。
**险处**：脚本有 `flock` 保护，**我若据此判「有孤儿」而不重挂，就会没有看守而不自知**——`qa` `02:15` 那个坑的镜像。
**于是我换成**：看 trail 最后一轮距今多久，>120 秒 ⇒ 没在跑。

**第二次换**（`15:16`，十分钟后）：`15:15:35` 我查，trail 距今 **31 秒**，判「有看守在跑」。而 `TaskStop` 报 `No task found`，自匹配安全的进程查法**又是零个**。
**真相是第三种**：看守 `15:15:04` 跑完最后一轮，**随即在 Monitor 过期那一刻被杀**；我 31 秒后去看，痕迹还新鲜。**我把「刚才还在跑」读成了「此刻在跑」。**

**两条判据的盲区是对称的，各约两分钟**：
```
ps 名单       把「不在跑」读成「在跑」      自己匹配自己
trail 新鲜度  把「已经死了」读成「还活着」   痕迹存活到下一个轮次期
```
**而它们都不是「不准」，是答的另一个问题**：`ps` 答「有没有一行长这样的命令」，trail 答「最近一次动作在何时」——**都不是「此刻它在不在跑」。**

**定论办法（`15:16` 起生效）：直接重挂，让脚本自己的 `flock` 来报。**
拿不到锁就打印「已有一个看守在跑，本实例退出」；拿得到就正常报轮次。**它看的是「我此刻去拿那把锁，拿不拿得到」——一个当下的、排他的事实**，而且代价为零，本来就要重挂。
**本期已兑现两次**：`15:16` 与 `16:16` 两次重挂，锁都没报冲突，看守随即正常报轮次。

> **换尺子的时候，很容易只检查它能不能答对旧尺子答错的那一格，而不去问它自己会在哪一格答错。**
