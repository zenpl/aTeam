## 结构性发现

### 一、一次失联被两份报告各漏了一半

那次失联是 `14:20:01 → 15:29:09`，整段 `4148` 秒，按补全口径超出 `4086` 秒。**它跨了窗口边界 `14:35:00`：**

```
落在 #250 的窗（12:35–14:35）：899 秒 ⇒ 扣掉一个正常轮 62s ⇒ 837 秒
落在 #251 的窗（14:35–16:35）：3249 秒 ⇒ 全部计入
合计 837 + 3249 = 4086 秒，与整段超出一致 ✓
```

**而 `#250` 我报的是「零在听 60 秒（窗内）」，并把整段算作「窗外那 4086 秒」。** 正确应是 `60 + 837 = 897` 秒。**这是本份的自我更正。**

**为什么会漏**：我算零在听的方法是**遍历窗内相邻两轮的间隔**。窗口开头那 54 分钟**一轮也没有**，于是它不产生任何「间隔」，方法看不见它——**本窗照那个方法算出来的是 `0` 秒。**

```
方法能看见：轮 → 轮 之间的缺口
方法看不见：窗口起点 → 第一轮       ← 本窗 3249 秒全在这里
方法看不见：最后一轮 → 窗口终点     ← #250 那 899 秒的一部分在这里
```

**补上的口径**：零在听要算三段——**窗口起点到首轮、相邻两轮之间、末轮到窗口终点**，三段都扣正常轮间隔 `62s`（且只扣一次，避免重复扣）。

**这是「量的是别的东西」这一行的第二个实例**，而它比第一个更难看：第一个（`#246`）是量错了单位，**这一个是方法有一整类情形看不见，而那类情形恰好是最严重的那种——严重到连一轮都没有。**

**「新容器天生就慢」这个替代解释被排除**：同一份脚本、同一台服务，重启后立刻回到常态。
