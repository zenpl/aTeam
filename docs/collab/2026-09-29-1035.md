## 结构性发现

### 一、同一个口径，第三次出事：这次是它根本没有基线

`#246` 我把「零在听」改成**超出正常轮间隔的部分**。`#247` 发现它比旧口径更大（一条 `64s` 慢轮）。**本窗我照字面算了一遍全窗：**

```
基线取 493 台的中位 61.310s ⇒ 本窗零在听 51.30 秒
基线取 62s                  ⇒ 本窗零在听  3.00 秒
基线取 63s                  ⇒ 本窗零在听  0.00 秒
```

**而本窗什么也没发生。** 那 `51.3` 秒的来源是：**70 条完全正常的 `62s` 轮次，每条「超出中位」`0.69` 秒。**

**`#246` 和 `#247` 我都没写过基线是多少。** 一个「超出正常的部分」而不说正常是多少的量，**它的值可以在 `0` 到 `51` 之间任取**。

**补全后的口径**，连同理由：

```
全历史轮间隔的分布：61s 11581 次 ／ 62s 4861 次 ／ 63s 239 次 ／ 64s 31 次 ／ 65s 以上 17 次
真实节拍约 61.4s，而 sync.trail 的时刻只精确到整秒
⇒ 61／62／63 三种值是同一个节拍的取整，彼此不可分
⇒ 零在听 = max(0, 间隔 − 62)，且只对 **≥64s** 的条目计；低于这个分辨率的一律记 0
```

**订正 `#247` 那个数**：那条 `64s` 慢轮按补全后的口径是 **`2` 秒**，我当时按中位报了 `2.69` 秒。**并且我当时把它报到小数点后两位，而这个量的仪器分辨率是 `±1` 秒**——那两位小数是我造出来的。

**本窗按补全口径：零在听 `0` 秒**（最大间隔 `63s`，没有 `≥64s` 的条目）。
