# aTeam 项目计划（重定）

2026-11-01 11:0x UTC，pm 写。**前一版的毛病不是排序错，是整个列表都在工具自己身上。** 这一版的论题只有一句：

> **这支队伍能设计、能实现、能自证；它不能交付。而「交付」卡在两个只有主人能做的动作上，而产品没有任何办法让这两个动作变便宜、可委派、或可追回。**
>
> 这不是运维问题，这是这个产品要解的问题本身。

---

## 一、进展（真的、可复用的）

1. **协作链条跑通了，而且快。** pd 定字 → pm 写可判的判据 → dev 实现并带反向注入，**十次重复，每次 3–20 分钟**。昨夜一次典型：20:25 定稿、20:26 开单、20:28 认领、20:33 交付。
2. **分工边界是被各自主动守住的**，这比规则存在更重要：措辞交回 pd 四次；范围交回 pm 两次（「要队列深度也算一条，另开一张单」）；**让闸红着等人五次**而不是绕过去；pd 明说「我没核那一行，把判断留给看得见代码的人」，而 dev 真去核了。
3. **闸与棘轮真的在挡人**，包括挡住它们的作者：113 处 `Rejected`；措辞棘轮拦住实现者两次；280 字闸拦住我两次；结构闸把一道闸从错误位置赶走一次。
4. **度量纪律长出来了**：谁量的写清楚、限度写出来、「没核过的转述」明写、同一结论要两个独立位置。昨夜至少六次是靠这条纪律抓住错误的——**包括我把一条不存在的事件当成交付那一次**。
5. **需求台账可回指**：O1–O8／T1–T15／M1–M10 加 ㉔–㉟，每条带「没有它会怎样」与现场出处。

**这五条是这个项目真正的资产。它们与「我们昨夜修了什么」无关，而与「一支 AI 队伍能不能自己保持诚实」有关。**

## 二、问题（按它离核心目标的距离排，不按技术严重度）

1. **产品二十六小时没有到达使用者。** 生产跑的是 10-30 的 sha；**92 件已完成的活在支上**；他那一页的内容是旧的、读起来不是人话；昨夜它还整段打不开过半小时。
2. **验收是结构性死锁。** 三方分离（定判据／干活／验收不能同一身份）＋在场无人持验收资格 ⇒ **24 件永远过不去**。这不是谁懒，是**规则在人手变薄时会把流水线锁死，而产品没有「验收者缺席」的出路**。
3. **队伍把力气花在自己的仪器上。** 过去八小时交付十件，**十件都是日志工具自身**（游标、预警、注入器、牌桌）。使用者那一侧只动了两件（时长梯子、两张卡）。**这是这个项目最危险的病：它会越来越擅长观察自己。**
4. **判断是瓶颈，而四类判断里三类只有主人能给**（验收资格、部署放行、产品范围）。**产品此刻没有任何机制让这三类变便宜**：不能批量、不能带条件委派、不能自动追回。
5. **每个节点都手搓了自己的求生装置**：pd 的影子游标、我重建的 CLI、各人的外层重起循环与唤醒过滤器。**T7／T8／T14 要的东西此刻不在产品里，而是各人自己造的。**
6. **代码没有单一真相线**：三条互不相干的历史、整合支落后 169 笔。于是「上线」变成一次 92 件的全有全无决定，而不是日常动作。
7. **自身可观测性是零**：昨夜宕机半小时，没有任何机器侧指标，**原因至今未知**，而它会再来。

## 三、计划（四阶段，每阶段只有一个退出判据）

### 阶段 0 — 解锁（只有主人能做，几分钟）

| 动作 | 谁 | 退出判据 |
|---|---|---|
| 把验收资格（R6）**临时、可追回**地授予 pd | human | 24 件开始出现 verdict |
| 放行那 92 件已完成的活上线 | human | `/health` 报回新 sha，使用者那一页的内容变了 |

**为什么是 pd**：这一批的判据是 pm 写的、实现是 dev 做的，**pd 两者都不是**，所以它验这一批不破坏三方分离——比起一个新 qa 会话更快更省。
**风险侧已有数**：峰值 RSS 300 MB（1gb 的三成）、两版差 4.9%、限堆加两次全量拉取不崩、退路（向前提交、内容回退）10-30 走通过。
**在此之前，队伍不开新单。** 已经执行中。

### 阶段 1 — 让代码只有一条线（队伍可自备，推送仍需主人）

**目标：让「上线」从一次 92 件的决定，变成一天数次的日常动作。**

- 把三条历史收成一条；交付支与整合支二选一，另一条退役。
- 准备好一个随时可推的 sha：构建绿、用例绿、deploy 与回滚命令写在一条 note 里。
- **退出判据：连续三天每天至少一次上线，且每次上线的决定耗时 < 5 分钟。**

### 阶段 2 — 让主人的判断变便宜（这才是产品的核心价值）

**目标不是让他少做判断，而是让他只做只有他能做的那一部分，并且做一次。**

| 做什么 | 退出判据 |
|---|---|
| 验收资格可声明、可带条件委派、可自动追回（「临时授予 pd，到期收回，全程留痕」） | 在场无人持 R6 时流水线**不**死锁 |
| 卡片带活的数字，答完即消失 | 他那一页上不再出现十一小时前的数（此刻那张写着「停了 10 件」而实际 24 件） |
| 全队皆死时的带外通道（T8） | **产品不在的时候，一小时内他仍然知道**——昨夜唯一的通道是宕掉的那台机器 |
| 一次拍板覆盖一批（而不是一件一张卡） | 一次点击放行一个批次 |

### 阶段 3 — 自身可观测性的最小集

- 机器侧：内存、重启、健康耗时的时间序列（此刻全无）。
- 读路径的代价：牌桌 10.4 MB 的大头在长文本字段（已量过，不是件数）。
- **退出判据：下一次宕机有原因可写。**

## 四、防复发：工具类工作的配额（这一条是给我自己的）

1. **使用者那一侧有未上线的交付时，不开工具类单**（正在执行）。
2. 恢复开单之后，**工具类不得超过在办任务的三分之一**，并且每一张要写明「它服务的是哪一条使用者可见的场景」——写不出就不开。
3. **每期报告第一行只答一个问题**：本期有东西到人手上吗。没有就三行写完：缺口、代价、哪一个判断能打开它。
4. 昨夜排进「队列能动之后」的四件工具活（㉟、空拉取那一格、按 id 读事件、职责分类声明）**整体降级到阶段 1 之后**；其中两件可能永远不值得做。

## 五、给评估者的三句

1. **这支队伍的协作部分已经可用**；需要评估的不是它能不能干活，而是**它交付所依赖的那两个人工动作该怎么降到几秒**。
2. **最该怀疑的是第三条问题**（队伍在优化自己的仪器）。它不是态度问题：当交付被锁死时，唯一还能做的事就是改工具——**锁死本身生产了这种偏移**。
3. **最有价值的一条产品洞察来自昨夜的失败**：判断的供给，而不是产能，是 AI 团队的瓶颈。阶段 2 整节都是围绕这一条写的。
