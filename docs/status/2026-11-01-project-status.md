## 二、技术

### 进展

- 架构是干净的：`packages/core` 纯函数且有测试（闸以 `Rejected` 的形式住在这里，113 处）、`packages/server` 用 `node:sqlite`、`packages/cli` 是节点用的客户端。
- 今晚八件交付都带**反向注入**证据（不是「测试通过」，是「把闸拿掉之后哪一格会红」），并且多次做到**按位置注入**而非按存在注入（例如把 `advance` 挪回原处就红）。测试总量约 1860 格，全绿。
- 中途立了一条实用口径并立刻见效：**「绿」必须分开说 build 与用例**——因为有一次 `pnpm -s build | tail -3` 把 tsc 的两行错误吞了，两笔交付的「全绿」其实只说了用例，而 build 从 `40a3e9e` 起一直红（`ad4e990` 修）。

### 问题（按严重度）

1. **生产宕机。** `/health` 与 `GET /` 不应答：dev 02:02–02:07 连发五次，全部 60 秒超时 0 字节（读数 `production:health.answers=false`）；我 02:13 在另一个节点上各量一次，15／25 秒 0 字节，而同一台对 `github.com` 是 0.9 秒 200。**00:33 同一条路还是 200／1.04 秒**，所以是这两小时里坏下去的。机器自 10-30 起已是 1gb，**所以当时那条「256MB 撑不住」的解释不成立**。
2. **此刻没有一个可以推上去的 sha**（dev 02:00 量出来的，我核过关键几行）：
   - 交付支 `c68165c` 长在 10-30 那次紧急回滚**之前**的线上（`git merge-base --is-ancestor origin/production HEAD` 答 no）；
   - 推它会把当时疑似压垮机器的那段代码推回去，**并且把唯一止住血的那一笔（256mb→1gb）带走**——交付支的 `fly.toml` 此刻仍写 256mb；
   - 把 production 合进来：**14 个文件冲突**，方向是「production 删了、交付支留着」，涉及约 1400 行，其中有别人交过、有的已验的活（`release.ts` 约 251 行等）。
   - 我的裁定：**不作废那 1400 行**（我一个人在一次 merge 里按掉别人的交付，不在 R8 权限内），**也不现在合并**；并立了口径：**产品决定不许搭在一次 merge 里走**。
3. **读路径是这套系统的结构性弱点。** 同一条 `/log?after=` 十分钟内量到 0.32 秒与 70.1 秒（dev）；一次只有两条事件的 `sync` 用了 235 秒（pd，读数 `production:sync.latency.s=235`，它自己补了边界：空批不可比）；牌桌回包 **10.36 MB**；日志约 14,400 条。提交 `1dc40e7` 里记着一条一致的观察：**写路径有增量缓存，读路径没有——读死了写还活着**（今晚正是这个样子：`/health` 不应答，而服务仍在落事件）。
4. **一族「仪器说假话」的缺陷**，今晚逐个被抓出来，修复都在支上、都未上线：
   - `/log?after=<id>` 会**不报错、不空、只是回答另一个问题**（问今天的 id，返回前天早上 11 条，JSON 完整闭合）——pd 02:02 的现场；
   - 客户端的报告不可信：`curl` 报 `000/0 字节` 而磁盘上躺着完整 JSON；写入报 `408`／`fetch failed` 而其实落了（我今晚五次），**我据此重发过一次，给 dev 发了两条一样的指令**；
   - `GET /event/<id>` 根本不是路由，所以对**真** id 也答 404（读数 `production:api.event.by.id=absent`）——**我有两条裁定据它写过字**；
   - 游标文件读出空被当成「没有游标」⇒ 自动打一发全量拉取（我中过一次，414 KB），而全量拉取正是牵涉过两次服务降级的那类请求（`t-351` 修，未上线）；
   - 渲染一崩就整批丢而游标照推（`t-340`／`t-343` 修，未上线）。
5. **三条互不相干的 git 历史**：整合支自己有两个根；pd 那棵树是第三个根；而那三道关键屏障**一笔都不在整合支里**（读数 `repo:barriers.in.integration=false`）。于是「谁从整合支构建，谁就有那个丢批的毛病」。

### 建议

- **B1（最高杠杆）**：把**读路径**当成下一个场景级工作，而不是又一批功能。它一个人解释了四件事：宕机、10.36 MB 的回包、70 秒的切片、以及全量拉取的危险。`t-322`／`t-323` 已在量代价，但它们还没被排进焦点——因为我在等一个可信的基线，而基线就是 `/health`。
- **B2**：先恢复生产（A1），再按三步重建可发车性：① 把那笔止血（`30aa368`，只有 fly.toml 一行）cherry-pick 进交付线；② 在 1gb 的机器上量「更重的那版」的真实开销（这件事**从未被量过**，10-30 的现场是 256mb）；③ 那 1400 行逐件重新落地，带「哪几件、谁交的、验没验」的清单，**作为一个独立决定交给 pd 与人**。
- **B3**：把今晚那一族「仪器说假话」的修复当作一批优先上线——它们不是功能，是**让我们量得准的前提**；今晚有五次「已修好的毛病又咬了人一次」，其中一次丢掉的是一条**指令**（不是 note）。

## 三、协作

### 进展（这一部分是真的跑通了，值得单独评估）

1. **链条稳定闭合，且很快。** 今晚重复八次同一条链：pd 定字（人可见的措辞）→ pm 把它写成可判的判据 → dev 实现并带反向注入 → 交付。单件耗时 3–20 分钟；一次典型的例子：pd 20:25 定稿、pm 20:26 开单、dev 20:28 认领、20:33 交付。
2. **分工边界守住了，而且是被各自主动守住的**，这比规则存在更重要：
   - dev 四次把**措辞问题**交回 pd，自己用占位往下走，不被措辞挡住；
   - dev 两次主动**把范围交回来**而不是顺手做掉（「要队列深度也算一条，另开一张单」）；
   - dev 五次**让闸红着等人**而不是绕过去（措辞棘轮要等 pd 通过才写）；
   - pd 明说「我没核那一行印不印验收人，把判断留给看得见代码的人」，**而 dev 真去核了**——判断权与证据权第一次完整分开。
3. **互相挡住错误是有效的**：三方分离一次没被破（没有人验自己的活）；pm 的判据被执行者挑出三处不足（一处把必要条件写成充分条件、一处引用了未核的事实、一处要求的东西早已落地）；dev 自己撤回过一条错误的 friction 并指出是自己的 build 红了。
4. **安全边界守住了**：没有人用使用者的身份写入；我拒绝给自己授予验收资格；没有人越权推生产；拒绝一律带规则名（`M4`），而且今晚被拒的几次都当场照改（例如读数的键写错、句子写错位置）。

### 问题

1. **验收是结构性堵死的，而且只有人能解开。** 24 件 `done` 没人能验：三方分离要求验收者既不是判据作者也不是实现者，而**在场的三个角色里没有一个持有验收资格（R6）**。这不是态度问题，是声明问题。
2. **焦点不是派活。** dev 那个会话只接「无人在办的 P0」和「pm 点名给 dev 的」（它那边的人 19 小时前让它收尾）。`t-341` 在焦点第一位挂了 50 分钟没人动，我点名之后一分钟被认领。**牌桌量得到「谁在听」，量不到「它会接什么」**，于是吞吐等于我点名的速度。
3. **期限在实测延迟下不诚实**：15 分钟的 ack 期限 vs 一次 235 秒的 sync；今晚出现过「pd 赶在 dev 的 15 分钟自设期限之前回话」的场面。**一个要靠收件人抢时间才兑现的期限，不是期限，是运气**（`t-336`）。
4. **pm（我）的开销偏高，而且偏向了错误的方向。** 我用大量篇幅写自己的认识论更正与仪器考古；使用者今天明确纠正了这一点。已改：报告第一行只答「本期有东西到人手上了吗」，更正写一行，队列不空且无人能验时不开新单。
5. **库存在堆积**：今晚我开了十一张单、撤一张，队列从 13 涨到 24，同期验收 0。pm 与 pd 已各自冻结（不开新单、不铸新要求）。

### 建议

- **C1（关键，且比「起一个 qa」更便宜）**：**把验收资格（R6）暂时授予 pd，而不是 dev。**
  理由：三方分离要求验收者不是判据作者、也不是实现者。今晚这一批的判据是 pm 写的、实现是 dev 做的——**pd 两者都不是，所以 pd 验这一批不破坏任何独立性**。授给 dev 会让它验自己实现的活（破坏 T5）；而起一个新的 qa 会话也行，但更慢、更贵。
  形式：一条可收回的声明变更，并写明「临时、针对此刻队列里这一批、事后收回」。**这是只有人能做的动作。**
- **C2**：把「这个节点会接什么活」变成牌桌上的事实（而不是只有 `cli_sha` 与「在听」）。最便宜的形状已经裁定：拿本机 `cli_sha` 与牌桌见过的最新那个比一比，并把限度一起印（说不出缺哪一笔、全队都旧时会说「你是最新」）。
- **C3**：保留这三条今晚被验证有效的协作纪律，把它们写进上岗说明：① 措辞先定稿、机制用占位先走；② 范围交回而不是顺手做掉；③ 让闸红着等人而不是绕过去。
- **C4**：把「判断的供给」当成这个产品真正要解的问题。今晚每一段停顿都是在等一个判断，每一段高产都发生在判断几分钟内能拿到的时候。**这意味着产品该优化的不是产能，而是「一个判断多快能拿到、拿不到时怎么不停摆」。**

## 附录（报告写完之后四小时内新量到的，按时间）

**① 「169 笔」这个说法是错的框法，正确的是「92 件已完成的活」**（dev 08:28 量，`origin/production..HEAD`）。
那 92 件里含三道屏障（`t-240`／`t-245`／`t-274`）与 **`t-300`**（「看守在服务端最忙的那一刻变聋：408／429 被归成我们自己的错」，status=verified）。
**所以待判的那件事不是「要不要赌 169 笔提交」，而是「要不要上线 92 件已完成、其中几件缺席的伤害今天可数」**。这一处是我（pm）反复用错了数。

**② 「1gb 够不够」已经量到，不必拿生产试**（dev 03:04，同一份 14,400 条日志、同一台机器、唯一的差是代码）：
```
峰值 RSS   production 294 MB   交付支 308 MB   差 +4.9%
限堆 700MB ＋两次全量拉取   峰值 285 MB，进程活着，没有 OOM
状态翻十倍（任务 720 → 7,200）  牌桌回包差 0.03%（它按绝对上限截，不随件数长）
最重的单个请求是全量拉取（＋70–80 MB），两版几乎一样
```
限度明写：日志是模板复制、不是 fly 那台机器、没有并发；所以 300 MB 是地板不是天花板，而离 1024 MB 有三倍余量。

**③ 10-30 那次回滚的前提被测量否掉。** 当时的怀疑是「新版 board/containment 更重，256MB 撑不住」；量出来两版是 294 MB 与 308 MB——**两版都塞不进 256 MB**。所以那次回滚没有治因，治因的是 `30aa368` 那一行（换 1gb）。**那约 1400 行是按一个此刻被否掉的假设回滚掉的**；它们该不该回来仍是产品决定，但依据变了。

**④ 生产在 02:02–02:13 整段不应答（含使用者那一页），02:50 自己回来了，没有人动过它。** 原因不明、自限、没有机器侧指标。**它会再来。**
而那半小时里**唯一能告诉使用者的渠道就是宕掉的那台机器**——卡片、牌桌、日志全在上面。这是 `T8`（「全队一起死时人在一小时内知道，要外呼地址」）的核心缺口，**而它此刻不存在于产品里**：那一次是靠会话里直接对人说才送出去的。建议把它排在读路径之后、其他功能之前。

**⑤ 牌桌那 10.4 MB 不是「件数太多」**（dev 量过，是条死路）：按件数翻十倍回包差 0.03%。大头在被上限放过的长文本字段（note／evidence／hint）。要瘦它，该量「哪几个字段吃掉了这 10.4 MB」。
