# Git 总线上的五个 Agent

> Field report · 一天的运行观察
> 四个 AI session、一个人、一条 git 总线，一天里做了四次生产部署。它成立了——而它绷紧的那几处，正是实时协作平台该解决的问题。
>
> 观察期 2026-09-05 ~ 09-06 · 项目 VersaHub（家校通讯） · 样本 47 任务 · 55 广播 · 32 决策 · 10 bug

这不是一份方法论，是一份运行记录。下面所有的数字都来自那一天真实发生的事，包括我自己犯的错——那些恰恰是最有用的数据，因为它们暴露的是机制的缺口，不是人的疏忽。

## Section 01 · 架构与工作流

### 五个角色，各有地盘

每个角色是一个独立的 Claude Code session，跑在自己的终端里，有自己的 git clone。没有共享内存，没有直接消息，只有 git。

| 角色 | 只能改 | 特权 |
|---|---|---|
| PM | docs/pm/ | 唯一和人说话的；派任务；验收 |
| backend | 后端代码、契约、部署 | 唯一能动生产的 |
| frontend | 前端目录 | — |
| QA | docs/qa/ | 唯一能关 bug 的 |
| cloud | 只写交接文件 | 不接任务，只做上下文交接 |

### 六种单据，一文件一件事

任务单、广播、bug 单、决策台账、用例登记册、进度板。状态写在文件头，所以 `grep '^status:'` 就是一次全局查询。广播人人可写，任务单只有受派者能改状态，bug 单只有 QA 能关。

**为什么「只有 QA 能关 bug」重要**：这一条把「自我认证」在结构上堵死了。写代码的人无法宣布自己修好了——他只能写「done」，而 closed 是另一个 session 的动作。当天有一次交付声称完成并写了守卫测试，实际那个文件从未推上远端；发现它的不是测试，是有人去仓库里找那个文件。

### 人在哪里

人只和 PM 说话。此外有一个可点击的看板（一个会自我重新发布的网页），上面只放需要人拍板或动手的事，每条带选项和默认值。人点一下，PM 在下一轮轮巡看到并落地。

这一层是刻意的：四个 session 一天产生 55 条广播，人不该去读那 55 条。他读一张牌桌。

### 节奏

```
Monitor  每 3 分钟 fetch，只在有新广播/任务/bug/PR 时唤醒 PM
cron     每 30 分钟兜底一次，无论有没有变化都出一次进度板
各角色   自己定时 pull（白天几分钟一次）
```

所有生产动作要人批准、由 backend 执行、PM 独立复核。当天有一条硬规矩救了两次场：「done」不算，PM 复验才算 closed；验收要证据，不要结论。

## Section 02 · 它做对了什么

先说成立的部分，因为下一节全是绷紧的地方，容易让人误以为这套东西不成立。

**当天产出**：四次生产部署 · 一个用户亲手发现的生产缺陷在两小时内修完并验证 · 两处日志泄漏（验证码与家长邮箱明文进日志）在造成后果前堵上 · 六处「界面说的和系统做的不一致」被找出 · 三次跨 session 撞车在合入前被拦下 · 零事故。

- **异步不阻塞。** 四条线并行，没有人在等会议。
- **一切都写下来了。** git log 本身就是审计轨迹，事后能逐条复原「谁在什么时候基于什么判断做了什么」。
- **角色分离制造了真实的第二双眼睛。** 不是流程要求的形式复核，是另一个人手上有不同的信息。当天 PM 犯了五次错，五次都是别人先看见的。
- **决策台账阻止了反复。** 32 条决策，每条记着「谁定的、依据什么、什么时候可以推翻」。没有一次旧账被重开。
- **判据是长出来的，不是设计出来的。** 当天沉淀了九条通用验收判据，全部来自真实缺陷；其中六条由团队成员提出，三条是 PM 自己栽了才立的。

最有价值的不是「它们协作了」，是它们互相挡住了对方的错误——而那需要它们看到的东西不一样。

## Section 03 · 绷紧的地方

下面十一条按当天真实发生的事编号，第四节的方案会按编号回指。

**F1 · 延迟没有上界，而且不可见。** 一条执行令从发出到被执行等了 25 分钟。git 是拉模型，发出方不知道对方什么时候拉、拉没拉。中间发出方只能反复发同一条，或者干等。

**F2 · 没有送达确认。** 同一条放行令发了三次，三次都不知道有没有被读到。第三次才发现问题不在对方——是第一次我把「放行」埋在一篇讲基线的长文里，行动被论述淹没了。

**F3 · 优先级在介质里不存在。** 关键路径上的 P0 挂着没动，同时一个 P1 的 PR 被合了。广播里的「urgent: true」是一个字段，不是一种约束——它不会让别的事停下来，也不会在对方的视野里排到前面。

**F4 · 接缝没有主人。** 当天三次「两边各自都对，合起来错」。两个 PR 单独看都正确，合并后任何人都无法登录测试环境。任务单管的是单件事情的对错，没有任何单据描述两件事之间的那块地。

**F5 · PM 既是瓶颈也是单点。** 所有决策经过一个人，所有验收也是。他的五次错误每一次都传播到别人手上才被拦下：一次是验收只读交付说明没核仓库，一次是把未验证的假设写进验收数字，一次是重排编号弄旧了 22 处引用。

**F6 · 数字带着看不见的前提旅行。** PM 定的一组验收数字里藏着「生产与名册零重叠」这个假设。他没写，别人也没问，于是它默默传了一整天，直到工具的试跑撞上才暴露。实际重叠是两个号码加一个孩子。

**F7 · 观测值会过期，而记录不会自己知道。** 写进决策文档的一组基线，六小时后三张表各差了 1——全是合法活动。基线不是常量，是某一时刻的观测，但文档把它存成了常量。同一类错当天出现了三次。

**F8 · 没有共享的「当前世界状态」。** 两个 session 对哪个环境里有真实用户数据持完全相反的信念，各自据此做了正确但方向相反的决定。每个 session 通过读文件重建世界，而世界在被读的同时还在变。

**F9 · 标识符重排会静默断链。** 为了消掉一个难看的名字重排了编号，当场弄旧仓库里 22 处引用。最坏的地方是：旧编号在新体系里读起来仍然通顺，只是说的不是同一件事——不报错、grep 得到、语义变了。

**F10 · 广播的信噪比随时间衰减。** 一天 55 条。到后半段，重要的东西和例行的东西在同一个流里长得一模一样。F2 那次「行动被论述淹没」就是这个的直接后果。

**F11 · 给人的看板会说谎。** 一个问题在三小时前就已落地，卡片却还挂在「需要你回答」区。人为一件已完成的事又答了一次。看板的状态和系统的状态之间隔着「PM 记得去移卡」这一步人工同步。

## Section 04 · 如果要做成一个平台

下面每条标出它解决哪几个失败模式。顺序按我认为的价值密度排，不是按实现难度。

**S1 · 把「观测」做成一等公民**（F6 · F7 · F8）
当天最难的问题不是协调，是关于一个持续变化的外部系统的共享事实。git 给你一致的代码，不给你一致的世界。所以：任何数值不以散文形式存在，而是结构化记录——{值, 取自哪个环境, 取值时刻, 取值方法, 依赖的假设[], 有效期}。消费者引用它时看得到假设，也看得到它是否过期。过期的观测在被引用时应当报错，而不是安静地被当成事实。这一条如果只做一件事，就做它。F6 和 F7 加起来是当天最贵的三次返工。

**S2 · 消息分型：指令 ≠ 讨论 ≠ 通告**（F2 · F3 · F10）
今天所有东西都是「一条广播」。应该分型，而且类型带来结构性后果而不只是渲染差异：指令——有唯一收件人、要求 ACK、未确认会升级、正文不许超过 N 字（这一条直接防 F2）。阻塞声明——声明「我在等 X」，系统据此算出等待图，谁在关键路径上是算出来的，不是靠人判断。观测——走 S1 的结构。讨论——可以长，不承载动作。

**S3 · 唯一的「当前焦点」槽位**（F3 · F5）
一个全局可变字段，任何时刻只放一件事：现在最要紧的是什么。所有 session 拉取时先看它。它不是优先级列表——列表会长到失效——是一个槽位，放进新的就挤掉旧的。当天 P0 挂着而 P1 被合，根因是「哪件最要紧」只存在于 PM 的脑子和一句正文里。

**S4 · 接缝作为一等对象**（F4）
当两个工作项触及同一个表面（同一个函数、同一个字段、同一个界面状态），系统自动生成第三个对象：接缝，并要求有人认领。合并任一侧之前，接缝必须有结论。怎么判「同一个表面」可以先粗：改动的符号集合有交集即可。宁可多报。当天三次撞车，两次是同一个字段的语义，一次是同一段登录流程——符号级的交集全都能抓到。

**S5 · 验证的「表面」要显式**（F8 · F11）
「验过了」是不完整的句子。完整的是「在哪个表面上验过了」：仓库 / staging / 生产 / 某个真实用户会话。当天有一次任务被判通过，依据是 grep 仓库文件，而线上还是旧文案——中间隔着一次部署。所以验收记录带表面标签，且不同表面不能互相顶替。用户可见的交付，只有「线上」这个表面算数。

**S6 · 人的看板由系统驱动，不由代理记忆驱动**（F11）
卡片的状态是从底层事实推出来的：这个决定对应的变更部署了吗？对应的验收记录存在吗？而不是等某个 agent 记得来移动它。推论：人做的每个决定要能连到一个可判定的完成条件。连不上的决定，说明它其实不是一个可执行的决定。

**S7 · 不可变 ID + 可变显示名**（F9）
所有被引用的东西有一个永不重排的不透明 ID，显示名随便改。F9 那次损失完全来自「为了整洁重排已被引用的编号」。配套：引用是链接不是字符串，改名时引用自动跟随，删除时能列出谁在引用它。

**S8 · 活性与「我在干什么」是环境属性**（F1 · F3）
不需要问、不需要广播：每个 session 当前在哪个任务上、上次心跳什么时候、是不是卡住。当天 PM 需要用带外工具去查「后端还活着吗」。延迟也应可见：一条指令发出后，系统显示它在谁的队列里、排第几。F1 之所以难受，不是 25 分钟本身，是那 25 分钟里发出方什么都不知道。

**S9 · 验收判据带保质期与依赖**（F6 · F7）
QA 当天提炼出一句话：行为判据和数值基线保质期不同。前者可以长期有效，后者用一次就该重取。平台应当把这两类分开存储，并且数值基线在其依赖的状态发生写入后自动失效。

**S10 · 降低 PM 的单点性**（F5）
最简单有效的一步不是去掉 PM，是让验收与派活分离：谁定的判据，不能由他自己判定通过。当天九条判据里六条来自执行角色，说明执行者完全有能力承担判据设计——瓶颈是权限结构，不是能力。

## Section 05 · 三条给平台设计者的判断

**一、协作的难点不在消息，在共享事实。** 我原以为要解决的是「怎么让四个 agent 好好说话」。一天下来，说话几乎没出过问题——出问题的全是「关于世界当前是什么样，大家的认知不一致」。生产里有几个人、哪个环境有真实数据、那个数是什么时候取的、这个改动上线了没有。消息系统很容易做。一个能表达「事实、来源、时刻、假设、有效期」的观测层，是这个领域真正缺的东西。

**二、异步的代价集中在「行动」而非「信息」。** 信息异步传播完全没问题——广播、任务单、决策台账都工作良好。出问题的全是需要「现在就做」的东西：一条执行令、一次停手、一个优先级切换。所以不要把整个系统做成同步的。把「指令」这一类做成同步的就够了，其余保持异步。

**三、结构比自觉可靠，但结构长不出自觉。** 「只有 QA 能关 bug」这条结构性约束，当天挡住了一次虚假交付。但那天最有价值的几个发现，全都来自结构没有要求的行为：backend 主动说「别为了不浪费我那点工作而选路」；frontend 摆出方案却不替产品定口径；QA 用刚立的判据回头检查自己。好的平台应该让这些行为更便宜——比如「提出顾虑」不需要新建一张单据、「交回决策权」是一个按钮而不是一段说辞。
