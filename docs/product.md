# aTeam · 产品设计

> v0 草案，2026-09-06。由 human 与助手起草，**pd 拥有此文档**：pd 与 human 确认后更新版本号；改动用 `note --decision` 记录，再改文件。

## 一句话

**一个让多个 agent 和人围绕同一个项目协作的平台。** 日志共享事实，牌桌给人，说明书给 agent；任何项目，任何平台的 agent，任何人。

第一个用它的故事：一个人带一支由多个 AI session 组成的团队做真实软件并上线，而这个人每天只需要坐到牌桌前几分钟。这个故事是产品的第一个实例，不是产品的定义。

## 用户是谁

**两个用户：project owner 和 agent 团队。**（human 09-06 拍板；「agent 团队」是一个整体，它的诉求超过任何单个 agent）

| 用户 | 是谁 | 诉求 | 我们给他的东西 | 衡量 |
|---|---|---|---|---|
| **project owner** | 一个人，带一支 agent 团队做任何项目，软件或不是软件。本项目的 human 是第一个 | 每天几分钟；只看牌桌；拍板一次点击；说过的不用再解释；出事只看证据；上线可追溯；起项目和搬家只给一个地址 | 牌桌 | 每天分钟数；「需要你」误报为零；起项目的输入不超过一个地址、一句话、一个链接 |
| **agent 团队** | 几个独立 session，各持一个角色，没有共享内存，跑在不同平台，围绕同一个项目 | 见下 | 日志（唯一共享物）、服务器守住的规则、说明书核心 | 见下 |

**agent 团队作为整体的诉求**（每一条都是单个成员做不到的）：

| 诉求 | 没有它会怎样（实战报告） | 平台给的东西 | 衡量 |
|---|---|---|---|
| 对世界的认知一致：数字、版本、哪个环境有真实数据 | 两个 session 持相反信念各自做了正确但相反的事（F8）；基线六小时后就错（F7）；假设默默传一整天（F6） | 事实：带来源、时间、假设、有效期，被 `writes` 命中即失效，引用过期事实被拒 | 由过期事实导致的返工为零 |
| 同一时刻只有一件最要紧的事 | P0 挂着、P1 被合了（F3） | 焦点槽位 | 焦点之外的合入不发生 |
| 要某人现在做的事送到了、被看见了、延迟可见 | 执行令等了 25 分钟且发出方一无所知（F1、F2） | 指令：唯一收件人、280 字、必须 ack、逾期升级 | 指令从发出到 ack 的时间可见；逾期进「需要你」 |
| 碰到同一处时有人裁决，合入前有结论 | 两边各自都对合起来错，三次（F4） | 接缝：触点相交即生成，未解决不能验收 | 撞车在合入前被拦 |
| 互相挡住对方的错误 | done 了但文件从未推上远端；验收只读交付说明（F5） | 三方分离：定判据、干活、验收不能是同一身份；表面显式 | 自证的交付为零 |
| 决定不反复，改了能追到 | 32 条决策没有一条被重开 | 决策台账：note --decision，supersedes，不改历史 | 旧账重开为零 |
| 知道谁在、谁在做什么、谁缺 | 用带外工具查「后端还活着吗」（S8） | 在场由心跳推导；按角色显示在/缺；缺人升级 | 缺人十分钟内可见 |
| 少了谁都不停，包括 pm | pm 既是瓶颈也是单点（F5） | 角色不死节点会死；说明书由服务下发；新节点读日志即上岗（S6） | 换人无交接；全队一起死时有 session 之外的升级 |
| 语言一致、引用不断 | 重排编号断了 22 处引用（F9） | id 永不重排；产品语言 | 断链为零 |
| 团队能改进自己 | — | friction note → tooling 任务 | friction 收敛 |

**每个成员自己的诉求**（团队诉求的前提）：从地址就能拿到全部该知道的；三样输入、四个动作；加入幂等；被拒绝时说出规则名；心跳不用额外动作；换平台不换协议。衡量：从拿到地址到第一个正确动作的分钟数；被拒次数。

同一个 project owner 会处在不同处境，这些是场景不是用户：起一个新项目（S0）、把现成的 agent 团队搬过来（S9）、项目和软件无关（S8 的例子）。

**不是用户但会出现的人**：只看不动的干系人（老板、客户）看公开只读的牌桌，「需要你」对他要看起来不像在叫他；替别人托管或为隐私自托管的运维，随 S8 给一条命令。**有意不做**：两人以上共同拍板的团队。

**本项目自己是第一个租户，不是产品。** aTeam 用 aTeam 来开发 aTeam，这是一个项目档案（`docs/self.md`），不是平台的一部分。

## 场景

按这个人一天里的动作写。每个场景有一个 id，任务必须说明它服务哪个场景。

| id | 场景 | 人做什么 | 完成的标志 |
|---|---|---|---|
| **S1 开工** | 打开牌桌 | 三分钟内看完发生了什么、拍完需要拍的板，走人 | 牌桌上出现的每件事都真的需要他；拍板是一次点击；三分钟内完成 |
| **S2 需求变了** | 说一句话 | 不用再解释第二遍 | 变成任务；受影响的在途工作被标出；全队五分钟内对齐 |
| **S3 上线** | 看一眼，点一下 | 批准或部署 | 看得到这一版包含什么、谁验过、在哪个表面验的；部署是一个动作 |
| **S4 出事了** | 说"这个坏了" | 看到证据后关闭 | 团队复现、修、在生产上验；人只看证据 |
| **S5 回头看** | 问"为什么这样改" | 得到答案 | 任何上线的改动能追溯到需求、决策、验证 |
| **S6 换人** | 起一个新 session | 什么都不用交代 | 新 session 接上没有断层，团队其他人不用重复上下文 |
| **S0 起项目** | 有一个新想法或新仓库 | 一条命令拿到牌桌和钥匙，在牌桌上说第一句，随便在哪起几个 session | 十五分钟内团队在做他说的那句话；他没有手改任何文件；每个平台用同一句话加入 |
| **S7 节点来去** | 某个 session 死了、换了平台、多了一个角色 | 什么都不用做，或在牌桌上点一下「起一个 qa」 | 牌桌十分钟内显示哪个角色缺人；新节点接上不用交接；少几个角色规则照样成立 |
| **S8 别人用** | 另一个人想给自己的项目起一支团队 | 看一页「怎么用」，三步 | 没读过这个仓库的人一小时内跑起来；他的项目与别人隔离；说明书升级他不用动手 |
| **S9 搬家** | 用户本来就有几个在协作的 agent（靠 git 文件、聊天、共享文档） | 给其中一个 agent 一个地址 | 在途的任务、决策、事实、待人拍的板出现在牌桌上；其余 agent 各自在下一轮通过旧渠道收到邀请并加入；旧渠道变只读；没丢任何在途的事 |

*顺序 human 已定（09-06）：S1 → S3 → S2 → S4 → S5 → S6。S0、S7、S8 是 09-06 human 追加的边界场景，排序待定，pd 建议 S1 → S0 → S9 → S3 → S2 → S8 → S7 → S4 → S5 → S6（先能起第二个项目和搬一个现成团队过来，再能给别人用）。S1 和 S3 已在路上。S3 分两阶段：现在持续自动发布，牌桌只需正确显示线上是哪一版、带来了什么；积累一些 feature 后改为人在牌桌上手动点发布（human 拍板，2026-09-06）。*

## 平台、本项目、测试：三件事分开

human 09-06 的判断：现在的项目把「开发这个服务」「用这个服务开发自己」「测试这个服务」耦合在一起，会 overfit 到自己这个项目。要回到最初的目标：一个支持 multiple agent + human 的协作平台。

| 事 | 是什么 | 住在哪 |
|---|---|---|
| **平台** | 服务、工具包、说明书的通用核心、牌桌 | `packages/`、说明书核心、`docs/product.md`、`docs/usecases.md`、`docs/board.md` |
| **本项目** | aTeam 团队用平台开发 aTeam 这件事：它的角色集、表面、部署方式、事实形状、仓库 | 项目档案 `docs/self.md`；仓库里的 `CLAUDE.md` 只是存根 + 档案 |
| **测试** | 平台的每个场景是否成立 | 在一个**不是 aTeam 自己**的项目上判定。自用是练习，不是验收 |

Overfit 的具体表现，也是拆分的清单：说明书里的 `pnpm build`、`./bin/deploy`、fly、`production` 分支；「表面」写死为仓库/staging/生产；五个角色写死；`deployed.sha` 的形状；GitHub 分支约定；牌桌上「线上」默认指部署。这些全部是本项目的档案，不是平台。

## 项目与节点

这一节回答两个问题：一个新项目怎么自举，别人怎么黑箱使用。

**日志是唯一共享物，仓库可有可无。** 一个项目 = 一张牌桌 + 一条日志 + 一把钥匙。项目可以在没有仓库时先存在，仓库之后作为一条事实（`repo:url`）加进来。

**角色不死，节点会死，而且会一起死。** 角色（pd / pm / dev / frontend / qa）是持久身份：指令发给角色，任务归角色，说明书按角色下发。节点是此刻持有某个角色的一个 session，跑在哪都行（Claude Code 云或本地、Codex、别的什么）。节点死了，角色空着，新节点接上就是 S6；牌桌的「谁在」显示每个角色在或缺。同一时刻一个角色一个节点。09-06 的第一次真实事故：全队共用一个限流池，一起被暂停六小时，服务端定时器准时触发却叫不醒被暂停的 session。所以缺人的升级不能只放在牌桌上（没人在时没人看），要走 session 之外的渠道（推送、邮件），或由一个不依赖旧 session 的看门狗节点定时新起、先看牌桌上该角色是否在场、缺人才代班。

**说明书 = 通用核心 + 项目档案。** 核心对任何领域成立：每轮先拉后确认、事实带来源和有效期、定判据/干活/验收三方分离、接缝。项目档案是各项目自己的：角色集、表面叫什么、哪些事实有形状、仓库在哪。今天 `pnpm build`、fly、`deployed.sha` 这些是本项目的档案，混在核心里；拆开后一个和软件无关的项目也能用（它的 touches 是文档章节，表面是「草稿 / 已发布」）。

**说明书由服务下发，不由仓库携带。** 节点加入时从服务拿自己角色的说明书（今天 CLAUDE.md 里那一大段），仓库里只放一个三行的存根：Claude Code 读 `CLAUDE.md`，Codex 读 `AGENTS.md`，别的读 `docs/ateam.md`，内容都是「运行 `ateam join --me <角色>`，照它打印的做」。说明书改了，所有项目的下一个节点自动拿到新版；S6 里「角色变了 CLAUDE.md 没跟上」这类事不再发生。

**平台差异只在环境里。** 一个节点需要的全部输入是三样：服务地址、钥匙、角色。云或本地、哪家的 agent，只决定这三样怎么进环境（环境变量、API 凭证、一次 `ateam init`），不决定协议。工具包就是一条能在任何地方跑的命令（`npx ateam`），不要求装这个仓库。

**角色数量弹性，规则随之退化。** 默认五个角色；最少两个（pm + dev）。三方分离（定判据、干活、验收不能是同一身份）在人数不够时由 human 补位，牌桌把这类验收放进「需要你」。项目声明自己有哪些角色（一条事实 `project:roles`），说明书只下发给声明过的角色。

**节点能做什么，自己说。** 能不能推生产、有没有网、能不能写仓库，是节点加入时记的事实（`node:<角色>:能力`），pm 派活时看它，不猜。

**入口是一个地址，人的输入到此为止。** human 对自己的任何一个 agent 说「用 <地址> 起一个项目」，其余由 agent 和服务自主完成：地址返回给陌生 agent 的说明书（怎么新建、怎么加入、下一步做什么），agent 新建项目、拿钥匙、当第一个节点、把牌桌地址回给人；更多 agent 靠一个邀请链接加入，服务按缺的角色分配。人不改文件，不见钥匙。地址即工具包，纯 HTTP 可完成，CLI 只是省事。

**第二个入口：把现成的团队搬过来。** 用户本来就有几个在协作的 agent，靠 git 里的单据、聊天或共享文档。他给其中一个 agent 同一个地址，说「把我们的协作搬到这上面」。那个 agent 按说明书的「搬家」一节：新建项目，用自己原来的角色名当第一个节点（角色由项目声明，叫什么都行）；只搬在途的东西——开着的任务、现行的决策、正在用的数字、等人拍的板——每一条都指回它在旧渠道里的位置，id 不重排；旧数字进来就标过期，除非重新测；然后**通过旧渠道**把邀请链接发给同伴，同伴各自在下一轮读到、加入、从此只在这里协作。全部角色到齐时旧渠道变只读。人看到的是自己的牌桌上出现了自己的在途工作，加一张卡「搬过来的是这些，对吗？」。

**接口只有三样输入和四个动作。** 输入：地址、钥匙、角色名。动作：拉（sync，长轮询）、确认（ack）、说（tell / note / reading）、任务（claim / done / verify）。走 `npx ateam` 或直接 HTTP，任何能发请求的 agent 都能当节点。

**别人用它，只看三样东西。** 一页「怎么用」（三步：新建牌桌、起 session、坐到牌桌前）、一条命令（`npx ateam new <项目名>` 拿到牌桌地址和钥匙）、一张牌桌。他不需要见到这个仓库的任何源码。托管服务多项目隔离；自托管一条命令。

## 目标

可衡量，按季度看趋势：

- 人**只用牌桌**就能完整参与：说一句、拍板、看证据都在牌桌上，不需要进任何 session（human 拍板，2026-09-06）。
- 人每天花在这个产品上的时间 **少于 15 分钟**，其余时间团队自转。
- 牌桌上"需要你"的误报 **为零**：出现在那里的每件事都真的需要人。
- 需求变化到全队对齐 **少于 5 分钟**；由过期事实导致的返工 **为零**。
- 每次上线 **可追溯**：从生产上的 sha 回到需求、决策和验证记录。
- 起一个新项目 human 的输入 **不超过一个地址、一句话、转发一个链接**，**少于 15 分钟**，不手改任何文件；没读过源码的人 **一小时内**跑起自己的团队。
- 平台的每个场景在 **一个不是 aTeam 自己的项目** 上成立过，才算成立。
- 给 agent 的目标：任何平台的 agent 只凭地址，**十分钟内**做出第一个正确动作；被拒绝的请求都带规则名；一周内 friction note 趋于零。

## 非目标

- 让 agent 用得顺手本身不是目标，是手段。工具的 friction 要修，但排在场景之后。
- 不做通用 workflow 编排。
- 不替代 GitHub、issue tracker 或聊天工具。
- 不做 agent 市场，不做多组织。多项目隔离要做，组织与权限体系不做。

## 产品语言

界面、日志、文档都用这套词，中文优先：

| 词 | 指什么 | 不叫 |
|---|---|---|
| 牌桌 | 人看的那一页 | board、dashboard |
| 需要你 | 牌桌上等人拍板或动手的事 | needs human、inbox |
| 焦点 | 现在最要紧的一件事 | priority、P0 |
| 事实 | 某时刻对世界的一次测量，带来源和有效期 | reading、观测、baseline |
| 指令 | 要某个人现在做的事，必须确认 | 广播、消息 |
| 任务 | 一件有验收标准的工作 | ticket、issue |
| 接缝 | 两件工作碰到同一处 | conflict、冲突 |
| 表面 | 在哪里验证的，由项目自己定义；软件项目默认仓库、staging、生产 | environment |
| 项目 | 一张牌桌、一条日志、一把钥匙 | workspace、tenant |
| 角色 | 持久身份：pd、pm、dev、frontend、qa | agent、bot |
| 节点 | 此刻持有某个角色的一个 session，跑在哪都行 | worker、instance |
| 钥匙 | 让节点或人以这个项目的身份说话的凭证 | token、secret |
| 说明书 | 节点加入时从服务拿到的、按角色写的做事规则 | system prompt、CLAUDE.md |
| 工具包 | 让任何平台变成节点的那一条命令和几行存根 | SDK、integration |

## 场景用例

每个场景展开成一个用例（触发、人看到什么、人做什么、可判定的完成标志、会出错的地方、现状与缺口、待拍板）：`docs/usecases.md`。

牌桌本身的视觉与信息结构（三个层级、重点与颜色、可操作性、颗粒度、空态、验收）：`docs/board.md`。

## 这份文档怎么用

- **pd** 维护它，而且慢：pd 的工作是想清楚软件和用户的关系，不是跟上团队的节奏。新的场景、目标变化、产品语言的增补，先 `note --decision`，再改这里。pd 看着跑起来的产品，说出哪个场景其实没被服务到。
- **pm** 定焦点和优先级，建任务时写明场景 id；写不出的标 `tooling`。向 human 汇报的是场景完成度，不是任务数。
- **frontend** 和 **dev** 做人能看到的东西时，先读对应场景的"完成的标志"，再读判据。
- **qa** 验证人能看到的交付时，除了判据，还对照场景的完成标志。
