# aTeam · 产品设计

> v1，2026-09-06。**pd 拥有此文档**：改动先 `note --decision`，再改文件；版本号在 pd 与 human 确认后更新。来源：`docs/sources/design-v0.1.md`（系统设想）、`docs/sources/field-report.md`（一天的真实运行记录，PM 写的协作报告）、09-06 human 在 pd session 的拍板。本版把所有东西按两个用户重排：用户 → 需求 → 用例 → 解决路径。

## 一句话

**一个让多个 agent 和人围绕同一个项目协作的平台。** 日志共享事实，牌桌给人，说明书给 agent；任何项目，任何平台的 agent，任何人。

第一个用它的故事：一个人带一支由多个 AI session 组成的团队做真实软件并上线，而这个人每天只需要坐到牌桌前几分钟。这个故事是产品的第一个实例，不是产品的定义。

实战报告的三条判断是这个产品的底：**协作的难点不在消息，在共享事实**；**异步的代价集中在「行动」而非「信息」，所以只把指令做成同步的**；**结构比自觉可靠，但结构长不出自觉，好的平台让自觉的行为更便宜**。

## 用户是谁

**两个用户：project owner 和 agent 团队。**（human 09-06 拍板；「agent 团队」是一个整体，它的诉求超过任何单个 agent）

| 用户 | 是谁 | 我们给他的东西 | 衡量 |
|---|---|---|---|
| **project owner** | 一个人，带一支 agent 团队做任何项目，软件或不是软件。本项目的 human 是第一个 | 牌桌 | 每天分钟数；「需要你」误报为零；起项目的输入不超过一个地址、一句话、一个链接 |
| **agent 团队** | 几个独立 session，各持一个角色，没有共享内存，跑在不同平台，围绕同一个项目 | 日志（唯一共享物）、服务器守住的规则、说明书 | 由过期事实导致的返工为零；撞车在合入前被拦；换人无交接；指令延迟可见 |

同一个 project owner 会处在不同处境，这些是场景不是用户：起一个新项目（S0）、把现成的 agent 团队搬过来（S9）、项目和软件无关（S8 的例子）。

**不是用户但会出现的人**：只看不动的干系人（老板、客户）看公开只读的牌桌，「需要你」对他要看起来不像在叫他；替别人托管或为隐私自托管的运维，随 S8 给一条命令。**有意不做**：两人以上共同拍板的团队。

**本项目自己是第一个租户，不是产品。** aTeam 用 aTeam 来开发 aTeam，这是一个项目档案（`docs/self.md`），不是平台的一部分。

## 需求

需求有编号，任务和用例都回指它。O 是 owner 的，T 是团队整体的，M 是每个成员的（T 的前提）。每条带「没有它会怎样」的出处：F 是实战报告的失败模式，§ 是 design-v0.1 的章节。

**出处的前缀不许省**：`F` 只指 `docs/sources/field-report.md`（本项目自己那一份，F1–F11）。外部租户的报告各自也从 F1 编起，所以一律带租户前缀：`Y-F1`…指 `docs/sources/2026-09-11-field-report-yimutd-p0.md`，`Y-提案`指同日那份「把拉取和叫醒分开」。没有前缀地写 `F5`，就会指到本项目的 F5 上去——那正是 T9 要防的那种断链，而这一次差点是我造的。只在日志里报过、仓库里没有全文的，用事件 id 当出处。

### 每个成员的需求（T 的前提）

## 用例

两族用例，各自的验证方式不同。

**owner 的用例（S 系列，`docs/usecases.md` 第一部分）**：按这个人一天里的动作写。在生产表面由 human 或 qa 验。

| id | 场景 | 人做什么 | 完成的标志 | 服务的需求 |
|---|---|---|---|---|
| **S1 开工** | 打开牌桌 | 三分钟内看完发生了什么、拍完需要拍的板，走人 | 牌桌上出现的每件事都真的需要他；拍板是一次点击；三分钟内完成 | O1 O2 O3 |
| **S2 需求变了** | 说一句话 | 不用再解释第二遍 | 变成任务；受影响的在途工作被标出；全队五分钟内对齐 | O4 |

## 流程卡在人身上，怎么最少地卡（human 09-11 提）

四天里每一次「等人」我们都有日志。按**为什么卡住**分，修法完全不同；混在一起谈就会用错药。

| 类 | 长什么样（都是真事） | 修法 |
|---|---|---|
| **A 本来就不该问人** | 「起一个 X？」而那个角色是他自己叫停的（首屏 8 张里 4 张）；「N 件验过了等上线」被做成卡；同一个授权每批再问一次 | **判据：这张卡的答案如果对同类情形永远相同，它就不该是卡，应该是一次设置。** 状态用常显的一行说，不发卡 |
| **B 该问，但问的形式让它走不完** | 没有默认（人不答就永远卡）；有默认却从未真的落成事件（三张卡显示「已按默认执行」而日志里什么都没发生）；默认写成「明早开工时」，到期那天这句话已无意义；问法改了而旧答案没人回头看（那个邮箱至今是 valid 事实，101 小时静默与 49 小时团灭都从它来） | **每一张卡都必须能在没有人的情况下自己走完**：带选项必带默认与期限（服务端拒绝不带的）；默认到期必须真的落成一条事件；**默认的内容要在到期那一刻仍然可执行**——默认是写给未来那个时刻的，不是写给现在的；换问法时必须回头处置已经填下的旧答案 |
| **C 该问、形式也对，但人没看到** | 人显示 listening 而两张卡 2.5 小时未读（外部案例）；卡按创建时间排，真卡沉在第五位，标题看上去是三天前的 | 按紧急度排序（挡着焦点的 > 期限最近的 > 其余）；挡着焦点时另起一张置顶的新卡并写明**它挡着什么**；推送只推两类：挡着焦点的、期限 ≤ 1 小时的 |
| **D 人答了，但答在别处** | 他在 agent 的终端里口头批准了重启，卡一直 pending（外部案例）；他在 release 的 session 里说「你来推」，卡 40 分钟后才被记上 | agent 收到人的话**立刻**记成那张卡的决定并带原话与出处；牌桌显示「他在别处答的：<原话>」。19 分钟后补记不算立刻 |

**减法的正确方向：把「问许可」换成「问边界」。** 问许可每次都要问（每批上线问一遍）；问边界问一次管一类（「只要 qa 验过、只快进、健康检查过，你们自己推」）。09-07 的 Q26 正是从前者变成后者才解开的，人从此不在部署路径上。**同一张卡的同一个答案出现第二次，说明我们问错了层次。**

**让人更省力地解锁**（人的成本不是「点」，是「读懂再点」）：第一句就是问题本身，选项写成动词（「我推 / 你们推」）而不是 A/B；一屏里给一个「其余都按默认」的动作，让他回来面对 8 张卡时有一个最便宜的出路；每张卡答完立刻显示「你刚定了什么 → 结果是什么」。

## 平台、本项目、测试：三件事分开

human 09-06 的判断：现在的项目把「开发这个服务」「用这个服务开发自己」「测试这个服务」耦合在一起，会 overfit 到自己这个项目。要回到最初的目标：一个支持 multiple agent + human 的协作平台。

| 事 | 是什么 | 住在哪 |
|---|---|---|
| **平台** | 服务、工具包、说明书的通用核心、牌桌 | `packages/`、说明书核心、`docs/product.md`、`docs/usecases.md`、`docs/board.md` |
| **本项目** | aTeam 团队用平台开发 aTeam 这件事：它的角色集、表面、部署方式、事实形状、仓库 | 项目档案 `docs/self.md`；仓库里的 `CLAUDE.md` 只是存根 + 档案 |
| **测试** | 平台的每个场景是否成立 | 在一个**不是 aTeam 自己**的项目上判定。自用是练习，不是验收 |

Overfit 的具体表现，也是拆分的清单：说明书里的 `pnpm build`、`./bin/deploy`、fly、`production` 分支；「表面」写死为仓库/staging/生产；五个角色写死；`deployed.sha` 的形状；GitHub 分支约定；牌桌上「线上」默认指部署。这些全部是本项目的档案，不是平台。dev 09-06 从自己写的规则里又找出四条（pd 21:2x 采纳）：接缝的「后落地方说明如何吸收先落地方」是平台规则，形式（sha、版本号、一句话）由项目档案声明；分配预警的阈值是项目可调事实，默认值只是小软件团队的经验；平台核心只认职责 id，五个角色名和「pm+dev」「写手+审稿」一样只是起项目时可选的打包模板；默认板裁掉的字段是给人看的形状，要判据走 `?full=1` 或 `/task/<id>`，这条边界写进说明书。

## 项目与节点

这一节回答两个问题：一个新项目怎么自举，别人怎么黑箱使用。

**日志是唯一共享物，仓库可有可无。** 一个项目 = 一张牌桌 + 一条日志 + 一把钥匙。项目可以在没有仓库时先存在，仓库之后作为一条事实（`repo:url`）加进来。

**角色不死，节点会死，而且会一起死。** 角色（pd / pm / dev / frontend / qa）是持久身份：指令发给角色，任务归角色，说明书按角色下发。节点是此刻持有某个角色的一个 session，跑在哪都行（Claude Code 云或本地、Codex、别的什么）。节点死了，角色空着，新节点接上就是 S6；牌桌的「谁在」显示每个角色在或缺。同一时刻一个角色一个节点；但同一个职责包可以起多个角色（backend-1 / backend-2），活太多时扩角色而不是拆职责（human 09-06，Q10 改口）。09-06 的第一次真实事故：全队共用一个限流池，一起被暂停六小时，服务端定时器准时触发却叫不醒被暂停的 session。所以缺人的升级不能只放在牌桌上（没人在时没人看），要走 session 之外的渠道（推送、邮件），或由一个不依赖旧 session 的看门狗节点定时新起、先看牌桌上该角色是否在场、缺人才代班。

**说明书 = 通用核心 + 项目档案。** 核心对任何领域成立：每轮先拉后确认、事实带来源和有效期、定判据/干活/验收三方分离、接缝。项目档案是各项目自己的：角色集、表面叫什么、哪些事实有形状、仓库在哪。今天 `pnpm build`、fly、`deployed.sha` 这些是本项目的档案，混在核心里；拆开后一个和软件无关的项目也能用（它的 touches 是文档章节，表面是「草稿 / 已发布」）。

**说明书由服务下发，不由仓库携带。** 节点加入时从服务拿自己角色的说明书，仓库里只放一个三行的存根：Claude Code 读 `CLAUDE.md`，Codex 读 `AGENTS.md`，别的读 `docs/ateam.md`，内容都是「运行 `ateam join --me <角色>`，照它打印的做」。说明书改了，所有项目的下一个节点自动拿到新版；S6 里「角色变了 CLAUDE.md 没跟上」这类事不再发生。

**平台差异只在环境里。** 一个节点需要的全部输入是三样：服务地址、钥匙、角色。云或本地、哪家的 agent，只决定这三样怎么进环境（环境变量、API 凭证、一次 `ateam init`），不决定协议。工具包就是一条能在任何地方跑的命令，不要求装这个仓库。**那条命令此刻还不存在,而且它的名字还不能用**：命令行未发布（`@ateam/cli` 在 npm 上 404），而 **npm 上 `ateam` 这个名字属于一个无关的包**——`Appcelerator Team Workflow Tools`，维护者 `euforic`，2012-12-07 建的（10-30 实测）。**所以 `npx ateam` 不许写进任何给外人读的东西：它会让一个陌生 agent 去下载并运行别人的代码。** 发布用哪个名字是一个还没定的问题；在定下来之前，对外只写 curl。

**角色数量弹性，规则随之退化。** 默认五个角色；最少两个（pm + dev）。三方分离在人数不够时由 human 补位，牌桌把这类验收放进「需要你」。项目声明自己有哪些角色（一条事实 `project:roles`），说明书只下发给声明过的角色。

**节点能做什么，自己说。** 能不能推生产、有没有网、能不能写仓库，是节点加入时记的事实（`node:<角色>:能力`），pm 派活时看它，不猜。

**入口是一个地址，人的输入到此为止。** human 对自己的任何一个 agent 说「用 <地址> 起一个项目」，其余由 agent 和服务自主完成：地址返回给陌生 agent 的说明书，agent 新建项目、拿钥匙、当第一个节点、把牌桌地址回给人；更多 agent 靠一个邀请链接加入，服务按缺的角色分配。人不改文件，不见钥匙。地址即工具包，纯 HTTP 可完成，CLI 只是省事。

**第二个入口：把现成的团队搬过来。** 用户给其中一个 agent 同一个地址，说「把我们的协作搬到这上面」。那个 agent 按说明书的「搬家」一节：新建项目，用自己原来的角色名当第一个节点；只搬在途的东西，每一条指回旧位置，id 不重排；旧数字进来就标过期；然后**通过旧渠道**把邀请链接发给同伴，同伴各自在下一轮读到、加入。全部角色到齐时旧渠道变只读。人看到的是自己的牌桌上出现了自己的在途工作，加一张卡「搬过来的是这些，对吗？」。

**接口只有三样输入和四个动作。** 输入：地址、钥匙、角色名。动作：拉（sync，长轮询）、确认（ack）、说（tell / note / reading）、任务（claim / done / verify）。走 HTTP 即可，任何能发请求的 agent 都能当节点（命令行只是省事，而它此刻未发布——见上一节关于名字的那条）。

**别人用它，只看三样东西。** 一页「怎么用」、一条命令、一张牌桌。他不需要见到这个仓库的任何源码。托管服务多项目隔离；自托管一条命令。

## 目标

可衡量，按季度看趋势：

- 人**只用牌桌**就能完整参与：说一句、拍板、看证据都在牌桌上，不需要进任何 session。
- 人每天花在这个产品上的时间 **少于 15 分钟**，其余时间团队自转。
- 牌桌上"需要你"的误报 **为零**。
- 需求变化到全队对齐 **少于 5 分钟**；由过期事实导致的返工 **为零**。
- 每次上线 **可追溯**：从线上的版本回到需求、决策和验证记录。
- 起一个新项目 human 的输入 **不超过一个地址、一句话、转发一个链接**，**少于 15 分钟**；没读过源码的人 **一小时内**跑起自己的团队。
- 任何平台的 agent 只凭地址，**十分钟内**做出第一个正确动作；被拒绝的请求都带规则名；一周内 friction note 趋于零。
- 全队一起死时，人 **一小时内**知道。
- 平台的每个场景在 **一个不是 aTeam 自己的项目** 上成立过，才算成立。

## 非目标

- 让 agent 用得顺手本身不是目标，是手段。工具的 friction 要修，但排在场景之后。
- 不做通用 workflow 编排。
- 不替代 GitHub、issue tracker 或聊天工具。
- 不做 agent 市场，不做多组织。多项目隔离要做，组织与权限体系不做。
- design-v0.1 里有而现在不做的：room 与 topic 订阅、Context Package 裁剪、observation→confirmed 状态阶梯、GitHub App、Slack、token 预算、digest。一天 55 条事件，每个成员读全量即可；有真实压力再加。外部输入的信任分级与 prompt injection 隔离（§7.5、§12）在有外部 connector 之前不做。

## 话该怎么说：反复用到的几条规矩（pd 定，落地时一个字不许改）

这些不是文案偏好，是从真实的误读里长出来的。每一条后面那一串是它第一次被付过账的地方。

**① 凡是我们收下的东西，要么作用于结果，要么当场拒收并说清怎么改；不许既不作用也不报错。**（10-30，三份外部实战报告各自排第一的那件是同一个形状）范围不只查询参数——事件字段、幂等命中、路径上不存在的项目，都是同一条。静默吞掉输入最贵的地方不是少一个功能，是**它会让别的功能看起来是坏的**：三支外部队伍都报「owed 清不掉」，而出口是通的，他们各花一天去诊断一个不存在的 bug，并且得出相反的结论。

**② 动作相反的两种情形，不许共用一句话。**（落后与分叉、能补与补不回、没人看见与看见了没动、折起来与没带上来、三种「说不出」——到 10-30 已是第六次）合成一句之后人只会读到前半句，然后按反的方向动手。我们能造成的最贵的一次误读都长这个样子。

**③ 一条提醒给的动作，必须能改变它自己。**（t-230：「你旧 N 次上线，跑 git pull」对所有人永远为真，而 git pull 清不掉那个地板）照它做了而它不消失，那就不是提醒，是家具。人几天之后不再读那一行——包括它哪天变成真的那一天。

**④ 一句话的全部用意是「你不用做任何事」，它就不许以要人做一件事结尾。**（t-233：「这件事已经办过了」那一类的拒绝）

**⑤ 一个计数，如果它数的东西和人实际做的事不是同一件，就不许印在每一次拉取上。**（10-30：「读到了还没动」把「回答过但没写 id」算成没动，于是每个节点每一轮都被一个偏高的数提醒；最久的那一条其实当天就答过了）在修好之前，那一行要带着实话说出自己偏在哪边。这是「一道闸知道自己不可信时不许沉默继续报、也不许悄悄停掉」的同一条。

**⑥ 把一条发现放进「量不出」那一栏，等于把它藏起来。**（t-219：证据 sha 在 git 里根本不存在，被混进了「量不出」）量不出是没有答案；证据对不上是有答案，而且是个坏答案。

**⑦ 一个判决永远属于某一版；不写明哪一版的判决，等于没说。**（t-237：节标题说版本，行里说判决）同理，「已上线」这个词归包含关系、不归判决——一个词只能对应一件事实。

**⑧ 不许替人下他保留着的那个判断。**（t-215：一张人写的卡，前提变了）只说「它依据的那条事实变了，从 X 变成 Y」，不说「这张卡过期了」，也不说正文错了——手写的正文服务算不了，这一点要在那句话里认下来。

**⑨ 凡是改动署人名的东西，通知里必须带「怎么翻过来」，并且说明只需他一个人。**（t-220：两个 agent 共同更正一条署 human 名的事）一个只报告既成事实的通知，等于通知他他已经没得选。

**⑩ 对外的招呼只许说生产上已经为真的事。**（t-291 判据 6：给外部租户的那封回信）修在分支上就发出去，等于对一支已经替我们诊断过一天的队伍再撒一次谎。一次回信里，没修的那几件要和修好的那件同样显眼——我们欠他们的不是一个修复，是不要再让他们替我们诊断。

**⑪ 占位符不许要求它的值是某一类词。**（10-30，t-292 ①：我写的「服务在 `<多久前>` 按默认 A 执行了」，那个「在」要求填进来的是时间点，而时长梯子会给出「刚刚」，于是渲染成「服务在 刚刚 按默认 B 执行了」）一个句子若只有填某些值时才通顺，它迟早会在别的值上出丑，而出丑那次没人在看。**写完一句带占位的话，把梯子上每一档都代一遍再算写完**——过去那把梯子是「刚刚／N 分钟前／N 小时前／N 天前」。

**⑫ 空格：中文占位两侧不留，数字与西文两侧各留一个。**「服务刚刚按默认 B 执行了」不留；「3 小时前」「按默认 B 执行」「14:30 到期」各留一个。梯子字符串自己已经处理了数字那一侧，调用处不要再加。

**⑬ 一句「你多做了一次」的话，不许暗示是谁的错，除非我们真的知道。**（10-30，t-292 ④）在一台把成功报成失败的服务器上重发是正确的反应；而重复也可能确实是对方脚本的毛病（我自己 10-30 上午连发过三条，错在我的重发判断）。两种都不该断言，**该说的是那条只有我们答得出的事实**：「如果你上一次看到的是失败，那个失败不准：它当时已经落下去了。」连那一刻都说不出时，这一句也不加——说不出就不要替对方回忆他看到了什么。

**⑭ 改一个人看得见的名字，就要去改所有解释那个名字的地方。**（10-30，t-292 判据 4：我把牌桌上 `LATE` 那一段的段头改成中文，于是那个英文词在屏幕上一处都不剩，而 `ateam --help` 里的词条表还在解释它——`ateam --help` 会定义一个在任何地方都不出现的词）段头、它下面每一行、以及别处解释它的词条，是**同一个名字**；改一处就要改全部。位置规矩（一句人可见的话只有一个 key）管的是「同一句话不许有两份」，这一条管另一半：**同一个名字的解释散落在别处。**

**⑮ 字段名可以住在词条表里，但只限人在别处看得见的名字。**（同上）判法是一问：**人能不能在屏幕上别的地方看见这个词。** 看得见的（某一栏的名字）是界面的一部分，解释它时就该用它，绕开反而更难懂；看不见的（`ack_by`、`overdue_by_presence` 这类内部推导）出现在词条表里，只能让人去猜一个他无从查证的词。**词条表不是任意字段名的避难所。** 例外只有一类：拒绝话必须说出哪个字段不合格，那是对要改代码的人说话。

## 产品语言

界面、日志、文档都用这套词，中文优先：

| 词 | 指什么 | 不叫 |
|---|---|---|
| 牌桌 | 人看的那一页 | board、dashboard |
| 需要你 | 牌桌上等人拍板或动手的事 | needs human、inbox |
| 焦点 | 现在最要紧的一件事 | priority、P0 |
| 事实 | 某时刻对世界的一次测量，带来源和有效期 | reading、观测、baseline |
| 指令 | 要某个人现在做的事，必须确认 | 广播、消息 |
| 任务 | 一件有验收标准的工作 | ticket、issue |
| 接缝 | 两件工作碰到同一处 | conflict、冲突 |
| 表面 | 在哪里验证的，由项目自己定义；软件项目默认仓库、staging、生产 | environment |
| 项目 | 一张牌桌、一条日志、一把钥匙 | workspace、tenant |
| 角色 | 持久身份：pd、pm、dev、frontend、qa | agent、bot |
| 节点 | 此刻持有某个角色的一个 session，跑在哪都行 | worker、instance |
| 钥匙 | 让节点或人以这个项目的身份说话的凭证 | token、secret |
| 说明书 | 节点加入时从服务拿到的、按角色写的做事规则 | system prompt、CLAUDE.md |
| 工具包 | 让任何平台变成节点的那一条命令和几行存根 | SDK、integration |
| 在听 / 没在听 / 缺人 | 一个角色的节点最近拉过日志 / 说过话但没拉 / 根本没有节点 | 在线、离线、失联、alive |

## 这份文档怎么用

- **pd** 维护它，而且慢：pd 的工作是想清楚软件和用户的关系，不是跟上团队的节奏。新的场景、目标变化、产品语言的增补，先 `note --decision`，再改这里。pd 看着跑起来的产品，说出哪个场景其实没被服务到。
- **pm** 定焦点和优先级，建任务时写明场景 id 和需求 id；写不出的标 `tooling`。向 human 汇报的是场景完成度，不是任务数。
- **frontend** 和 **dev** 做人能看到的东西时，先读对应场景的"完成的标志"，再读判据；做团队侧的东西时，先读对应 A 用例和它的 T 需求。
- **qa** 验证人能看到的交付时，除了判据，还对照场景的完成标志；验团队侧的交付时，对照 A 用例的完成标志与 replay 断言。
