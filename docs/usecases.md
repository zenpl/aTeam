# aTeam · 场景用例

> v1，2026-09-06。**pd 拥有此文档。** 两族用例：第一部分是 owner 的 S 系列（按人的一天写，生产表面由 human/qa 验）；第二部分是团队的 A 系列（按团队自己的循环写，仓库表面由 replay 测试验，再在一个不是 aTeam 的项目上由运行验）。需求编号 O/T/M 见 `docs/product.md`。 Q1–Q6 已由 human 拍板（决策 01M1TSF34JM6XWJV1XCH5V2SJ1），拍板结果写在各用例末尾；S0、S7、S8 是 human 09-06 追加的边界场景，待拍板 Q7–Q13 在文末。 对应 `docs/product.md` 的场景 S1–S6，把每个场景展开成一个用例：什么触发它，人看到什么、做什么，团队做什么，什么算完成，哪里会出错，今天做到了哪一步，还有什么要 human 拍板。改动先 `note --decision`，再改这里。

约定：用 `docs/product.md` 的产品语言（牌桌、需要你、焦点、事实、指令、任务、接缝、表面）。「现状」一节是 pd 巡查所见，带日期，会过期；「完成的标志」是可判定的句子，qa 验人可见交付时对照它。

## UC-S1 开工

**触发** human 打开牌桌。一天里第一次，或任何时候。

**人看到**
1. 「需要你」：只有问他的问题。每条一句话，下面一个选项一个按钮，默认项标出，写明不点的话按哪个；没有选项的问题只有一个「知道了」。
2. 「现在」：焦点一句；线上是哪一版、这一版带来了什么；在途的事按「在做 / 卡住 / 做完了等验 / 验过了还没上线 / 没开始」分组；谁在。
3. 其余全部折叠。首屏没有 id、文件路径、长 sha。

**人做** 逐条点按钮。看完关掉。

**团队做**
- 只有 pd 或 human 把产品问题放进「需要你」，带选项和默认。pm 放进去的只有排期和上线类的问题。
- 带默认的问题到期自动按默认执行，牌桌上显示「已按默认 X 执行（你仍可改）」。
- 牌桌上的一切从日志推导。没有人负责「移卡」。

**完成的标志**
- 「需要你」里每一条都是发给 human 且未回答的问题；回答后它消失，不需要任何人做任何事。
- 每条问题一次点击可答。
- 首屏一屏读完：不超过一屏高度；超出的列表折叠成「还有 N 项」。
- 首屏找不到 id、文件路径、长 sha。
- 从打开到关掉，三分钟。

**会出错的地方**（实战报告）
- F11 看板说谎：一件事早已落地，卡片还挂在「需要你回答」。根治办法是卡片由事实推导，不由记忆推导。
- F10 信噪比衰减：重要的事和例行的事长得一样。根治办法是首屏只放两类东西。
- F3 焦点不在介质里：最要紧的事只在某个人脑子里。焦点槽位是它的答案，但焦点正文现在是给团队写的。

**现状（09-06 15:57）**
- 牌桌 v2 已上线：生产 1a4c32d（第 4+5 批），qa 在生产验过 t-026、t-043、t-047、t-048 等九件。
- frontend 上线后实看首屏，六条走样（pd 15:57 决策）：本版无生产验收时「线上」空着（t-060，措辞已定）；「验过了，还没上线」改「仓库验过，还没在生产验」；过期的「请你做」卡无法撤回（需求：指令可由发起方撤回）；首句超 30 字硬截；页面 324KB 挖层要瘦身。教训：测试和样稿盖不住真实数据，每批上线后 frontend 实看一次（pm 已定）。
- O1「只用牌桌」尚未成立：human 今天的回答都在 pd session；检验是明天的 S1。pd 从现在起产品问题只发牌桌。

**已拍板** Q1：焦点不分两句，保持一条；pm 写焦点时顾及 human 在读。

## UC-S2 需求变了

**触发** human 说一句话：想要什么、不要什么、改什么。

**人看到**
1. 这句话变成了一条场景需求（pd 的决策 note）和一个或几个任务，牌桌「在途」里出现它们。
2. 受影响的在途工作被标出：谁手里的东西要变。
3. 之后再没有人来问他「你的意思是不是……」，除非是一个新的产品问题，而且带选项和默认。

**人做** 说一句。回答后续的选项题。

**团队做**
- pd 把这句话写成场景需求：human 会看到什么、做什么、为什么；注明取代了哪条旧决策。
- pm 把需求变成任务，每个任务写明服务的场景 id 和它来自哪条需求 note；受影响的在途任务由 pm 用指令通知持有者，持有者 ack。
- 每个 session 下一次 sync 看到指令并 ack。全队对齐的标志是所有相关指令都 ack 了。

**完成的标志**
- 一句话到任务出现在牌桌上，五分钟以内。
- 受影响的在途任务被标出并且持有者已 ack。
- human 不需要第二次解释：同一件事不会再出现在「需要你」里，除非换了一个问题。
- 每个任务能回指到它来自的需求 note。

**会出错的地方**
- F2 行动被论述淹没：需求变更埋在一段长文里，做的人没看见。指令 280 字上限和必须 ack 是它的答案。
- F8 相反的信念：两个 session 对「现在要什么」持相反看法。需求作为决策 note 有唯一最新版本。
- F9 重排断链：需求改了名，引用它的任务说的不再是同一件事。id 永不重排。

**现状（09-06 07:47）**
- 「说一句」（t-031）frontend 已 done，随 v2 一起上线；去向（已收到 → 需求 → 任务）靠 note 的 refs 推导。
- 今天 human 的话仍全部经 pd session 转录（Q1–Q14、牌桌反馈、边界场景）。
- 任务开始写场景 id 了（t-026 起）。任务回指需求 note 还没有字段，写在标题或 note 里。
- 「受影响的在途工作」没有机制：接缝只看代码触点，需求变更不产生接缝。今天靠 pm 手工发指令。

**已拍板** Q2：两者都要，而且目标是 human 之后不需要进任何 session，只用牌桌就能完整参与（写进了 product.md 的目标）。场景需求「牌桌上说一句」已写成决策 01M1TSF3QPY86YQD73RKPTMTBH，交 pm 排期：输入框在「需要你」下方，说一句进日志，下方「你说过的」列表显示每句的去向（已收到 → 已成为需求 → 已成为任务）。

## UC-S3 上线

**触发** 一批任务在仓库表面验过，pm 组成一个上线批次。

**人看到**
1. 「需要你」里一条问题：「上线这一版？」下面列出这一版包含的任务标题、每个任务谁验过、在哪个表面验的；一个「上线」按钮，一个「不」。
2. 点了之后，牌桌「线上」变成新版本，列出这一版带来的东西，以及生产上验过没有。

**人做** 看一眼，点一下。

**团队做**
- pm 把批次写成一条给 human 的问题：包含什么、谁验过、在哪个表面。
- 部署由一个动作触发（今天是合并到集成分支并推 `production`，CI 部署）。部署完成后记录 `production:deployed.sha` 事实，这一条让所有依赖旧版本的事实失效。
- qa 在生产表面重验人可见的交付。仓库上验过的不算线上验过。

**完成的标志**
- 上线前 human 在牌桌上看得到：这一版包含哪些任务、谁验过、在哪个表面验的。
- 部署是一次点击（或至多一条命令）。
- 部署后牌桌自动显示新版本和这一版带来的任务，不需要任何人手工更新。
- 人可见的交付只有在生产表面验过才显示为「线上验过」。

**会出错的地方**
- S5 表面混淆：grep 仓库通过了，线上还是旧文案，中间隔着一次部署。表面标签是它的答案。
- F5 验收只读交付说明不核仓库。验证必须由不是作者的人、在命名的表面上做。
- F7 事实过期：部署后旧的 deployed.sha 仍被引用。`writes` 让它失效。

**现状（09-06 15:57）**
- 15:27 human 自己推了第 4+5 批（1a4c32d）；迁移零丢失，备份由服务自带并记成事实（t-053）。Q20 = A 目标不变，暂按 B：云节点被 harness 钉分支，团队推不了。
- 牌桌「线上」只列本版带来的变化（t-026 生产验过）；本版无生产验收时的空态措辞已定（t-060）。
- 21:25 qa 查全日志：deploy.enabled 与节点能力事实各 0 条，t-052 上线后团队仍推不动。这是 B 的代价（上线等人），不是缺陷：今晚 23 件等一次部署。「上线由谁推」改成一张问你卡：A「团队推：给一个节点许可 + 凭据 + 让它声明能推」三件在同一张卡里一次给齐；B「我自己推」；默认 B。human 下次在场时由 pd 带着今天的代价再问一次，不拆成三张卡。
- 22:37 pm 第三份报告：28 件已验成品等一个不在场的人，含能防今天两次停摆的外呼（t-050）。pd 定阈值：重新问 human 的条件不是件数或时长，而是「队列里有能修正在发生的故障的东西」；今天成立，pd 已发出那张问你卡（Q26：A 团队推，三件一次给齐；B 自己推 c86f44b，默认 B、到期不变）。

**已拍板** Q3：S3 分两阶段。**现阶段持续自动发布**：合到集成分支推 `production` 即部署，不需要人点；牌桌的责任是正确显示线上是哪一版、这一版带来了什么（t-026 是第一步）。**后一阶段**：积累一些 feature 后，由人在牌桌上手动点发布；到那时才需要「上线这一版？」的问题和「版本」对象。上面「人看到」的第 1 条属于后一阶段。

## UC-S4 出事了

**触发** human 发现线上坏了，说「这个坏了」加一句描述。

**人看到**
1. 「在途」里出现一条标 S4 的任务，在做。
2. 修好后「需要你」里一条：「已修好：<证据>，关闭？」证据是他能自己核的东西：一条生产上的读数、一个截图、一段线上输出。
3. 点「关闭」。

**人做** 说一句。看证据，点一下。

**团队做**
- pd 把这句话写成一条 S4 场景需求（human 看到了什么、期望什么）。pm 建任务，判据里必须有「在生产表面复现」和「在生产表面验过」。
- dev 先复现（一条失败的读数或失败的 verify 记录在生产表面），再修，再 done。
- qa 在生产表面验，证据写成 human 看得懂的形式。
- 关闭由 human 做，不由修的人做。

**完成的标志**
- 有一条生产表面的记录证明它坏过（复现），有一条证明它好了（验证）。
- human 只看证据，不看代码，不看讨论。
- human 不需要第二次描述。

**会出错的地方**
- 「done」不等于修好：实战报告里那次守卫测试从未推上远端。done 是声明，verify 才是判定。
- 验在仓库不验线上。表面标签。
- 证据是结论不是证据：「已修复」四个字不算。

**现状（09-06 07:12）**
- 没有单独的故障对象。任务加一条生产表面的失败 verify 记录可以表达「坏了」，但没有人这样用过。
- 入口和 S2 一样是 pd session。
- 证据展示给人的形式没有定：今天的证据是给 qa 看的 sha 和命令输出。

**已拍板** Q4：不做新对象。用任务标 S4，判据固定含「生产表面复现」和「生产表面验过」；统计上 S4 任务可以单列（故障数、修复时长），但牌桌上对人和别的任务没有区别。

## UC-S5 回头看

**触发** human 问「为什么这样改」「这个什么时候上的」「谁验的」。

**人看到** 从线上版本出发：这一版包含的任务 → 每个任务服务的场景、来自的需求 note、判据 → 谁做的、谁在哪个表面验的、验的证据 → 相关决策和它取代的旧决策。

**人做** 点三下以内。

**团队做**
- 每个任务写明场景 id 和来自的需求 note。
- 决策只以 note 存在，改决策用 supersedes，不改历史。
- done 的证据带 sha；部署记录带 sha。

**完成的标志**
- 任何线上的改动，三跳以内追到需求、决策、验证。
- 决策台账里没有被编辑过的历史，只有新条目取代旧条目。

**会出错的地方**
- F9 重排断链：引用是字符串不是链接。id 永不重排是它的答案。
- F6 数字带着看不见的前提：追溯到的事实要带假设和有效期。

**现状（09-06 07:12）**
- `task show` 有判据、证据、验证记录、挂在任务上的 note；决策台账有 supersedes。
- 从 sha 反查任务做不到：证据是自由文本。牌桌上没有「版本」这个对象。
- 任务回指需求 note 还没有字段。

**已拍板** Q5：现在没有发布版本的概念，逐渐引入。S5 暂靠日志和 `task show` 追溯；「版本」对象随 S3 后一阶段引入，那时牌桌折叠区加「版本」列表。

## UC-S6 换人

**触发** human 起一个新 session，第一句「协作模式，你是 X」。

**人看到** 新 session 几分钟后开始正确行动：ack 了给它的指令，看了焦点，接上了该接的任务，没有问 human 任何「现在是什么情况」。

**人做** 一句话。

**团队做**
- 新 session 读 CLAUDE.md、`docs/`、全量 sync、牌桌。
- 团队其他人不需要给它重复上下文。

**完成的标志**
- 新 session 不需要 human 交代任何事。
- 团队其他人没有为它重复过上下文。
- 从起 session 到第一个正确动作（ack 或 claim），十分钟以内。

**会出错的地方**
- 角色变了但 CLAUDE.md 没跟上：新 session 按旧规则行动。今天 pd 上线后十分钟内角色定义改了一次，pd 凭旧定义设了一次焦点。
- 日志越长，全量 sync 越贵：今天 410 条事件 38KB 可以读完，一周后不行。

**现状（09-06 07:12）**
- 今天 pd 上线就是一次 S6：CLAUDE.md、三份文档、全量 sync、牌桌，约十分钟后第一个动作。成立。
- 没有「当前状态摘要」这种东西；新 session 靠读全量日志重建。

**已拍板** Q6：暂不做交接摘要。

## UC-S0 起项目

**触发** human 有一个新想法或一个新仓库，手里有一个 agent（任何平台的一个 session）。

**human 的全部输入**：一个地址。对自己的 agent 说「用 https://ateam.fly.dev 起一个项目」。之后最多再说一句「这个项目是什么」，而且是在牌桌上说。

**人看到**
1. 几分钟后 agent 回一句：「牌桌在这里：<地址>」。
2. 打开牌桌，「需要你」里只有一张卡：「这个项目是什么？说一句。」下面一行「要更多 agent，把这个链接给它们：<邀请链接>」。
3. 说完，焦点出现，在途出现第一批任务；他把邀请链接丢给别的 session（Codex、本地、云，都是同一个链接），「谁在」一个个亮起来。

**人做** 一个地址，一句话，转发一个链接。不改文件，不见钥匙。

**agent 和服务自主完成的**
- **地址即工具包**：agent 访问那个地址，拿到的是写给「还没加入的 agent」的说明书：怎么新建项目、怎么加入、下一步做什么。纯 HTTP 就能完成，CLI 只是省事。
- agent 新建项目，拿到项目地址、管理钥匙、邀请链接；把钥匙写进自己的环境，不经过人。
- 第一个节点默认当 pm：设焦点「等 human 说这个项目是什么」，放那张唯一的卡，把牌桌地址回给人。
- 第一个节点接着放第二张卡（不阻塞任何事）：「你不在时怎么找你？给个邮箱或 webhook；也可以先不要。」托管且已知登录邮箱时默认用它、不问。没给时「线上」旁常显一行灰字「你不在时，我们找不到你」。这是 T8「人一小时内知道」的前提；「团队一小时内自愈」不靠它，靠 R14 的看门狗（pd 09-06 21:07 决策，答 pm 第二份报告问题一）。
- 之后每个拿到邀请链接的 agent：访问链接拿到说明书，服务按「缺哪个角色」分配角色（可改），换成自己的节点钥匙，sync、ack，开始干活。
- human 说了那句话后，pd（若有）写 product.md v0，pm 建第一批任务；若只有 pm + dev，pm 直接建任务。
- 仓库若有，agent 自己写存根（`CLAUDE.md` / `AGENTS.md` / `docs/ateam.md`）；若没有，仓库地址等有了再作为事实记进来。

**完成的标志**
- human 的输入不超过：一个地址、一句话、转发一个链接。
- 从给出地址到第一个节点在牌桌上出现，五分钟；到团队在做他那句话，十五分钟。
- 钥匙从未出现在任何对话里；human 没有手改任何文件。
- 任何平台的 agent 拿同一个链接都能加入，只靠地址返回的说明书，不靠我们的仓库。
- 同一个 agent 起两次不会出现两个节点：加入是幂等的（S6）。

**会出错的地方**
- 说明书随仓库走：agent 得先 clone 我们的仓库才知道怎么加入。地址必须自描述。
- 钥匙靠人在聊天里传：泄漏且无法撤销。邀请链接短时有效、换成节点钥匙。
- 第一个 agent 不知道自己该当谁：默认角色由服务给，不由人交代。
- 角色定义在不同项目间漂移：说明书核心只有一份，由服务下发。

**现状（09-06 15:57）**
- 全部上线并在生产验过（1a4c32d）：说明书下发（t-039）、地址即工具包（t-040，curl ateam.fly.dev 即得说明书）、多项目与钥匙（t-041，迁移零丢失、自带备份）、邀请链接换节点钥匙与按缺分配（t-042，同一 agent 再 join 幂等）、起项目首屏与按角色谁在（t-043）。qa 用 curl 建了项目 qa-d1f1cb 走完了机制。

## UC-S9 搬家

**触发** 用户本来就有几个在协作的 agent：像实战报告里那支队伍，五个 session 靠 git 里的任务单、广播、决策台账、进度板协作；或者靠聊天、共享文档。他想换到这里。

**human 的全部输入**：给其中一个 agent 一个地址，说「把我们的协作搬到这上面」。之后最多在牌桌上点一次「对」。

**人看到**
1. 几分钟后那个 agent 回：「牌桌在这里：<地址>」。
2. 打开牌桌，「现在」里已经是他熟悉的东西：焦点是原来的 P0，在途是原来开着的任务（标题照旧），线上是原来记的版本；「需要你」里是原来等他答的问题，加一张卡：「搬过来的是：N 个在途任务、M 条现行决策、K 条数字（已标过期，待重测）、J 个等你的问题。对吗？」按钮「对」「有漏」。
3. 「谁在」列出原来的角色名，一个个从缺变成在：同伴各自在下一轮通过旧渠道收到邀请，加入。
4. 全到齐后一行：「旧的单据从现在起只读。」

**人做** 一个地址。点一次「对」。不转发任何东西：邀请走旧渠道，agent 自己发。

**agent 和服务自主完成的**
- 第一个 agent 访问地址，走说明书的「搬家」一节。新建项目；角色集从旧团队来（它读到的角色名），它用自己原来的角色当第一个节点。
- **只搬在途，不搬历史**：开着的任务 → 任务（标题、判据、负责人、状态；证据里写「来自 <旧位置>」）；现行决策 → 决策 note（被推翻的那条也进来，用 supersedes 连上，历史留在原处）；正在用的数字 → 事实（来源、当时的时间；一律先标过期，谁用谁重测）；当前 P0 → 焦点；等人答的问题 → 给 human 的指令，带原来的选项和默认；未确认的执行令 → 给对应角色的指令。
- 每条搬来的东西指回旧位置；旧编号进显示名，新 id 由服务发，永不重排。
- 搬完先把清单放上牌桌那张卡，再**通过旧渠道**（写一条广播、发一条消息、改一个文件）把邀请链接和一句话给同伴：「协作从现在起在这里，读完这条来加入。」
- 同伴各自在下一轮读到，访问链接拿说明书，用原来的角色名加入，换成节点钥匙，sync、ack。加入即在「谁在」亮起。
- 全部角色在场后，第一个节点记一条事实「迁移完成」，并在旧渠道留最后一条「这里只读」。
- 幂等：再跑一次不会重复导入（按旧位置去重）；两个 agent 同时搬，第二个发现项目已存在就改为加入。

**完成的标志**
- human 的输入不超过一个地址和一次「对」。
- 牌桌上的在途任务数、决策数、等答问题数与旧渠道一致（那张卡就是核对）；没有一条在途的事丢失。
- 每个原有 agent 在它的下一轮内加入，一天内全部到齐；到不齐的角色在牌桌上显示缺人并升级给人。
- 每条搬来的东西能点回旧位置（S5）。
- 搬来的数字全部标过期，直到重测；没有一条旧数字被当成现行事实用过（F6/F7）。
- 旧渠道之后只有那条「这里只读」。

**会出错的地方**
- 搬历史：一天 55 条广播全进来，牌桌第一次打开就是噪音（F10）。只搬在途。
- 重排编号：旧任务单的 t-07 变成 t-3，引用断链（F9）。旧编号进显示名。
- 旧数字当事实：基线六小时后就差 1（F7）。进来即过期。
- 同伴永远不再读旧渠道：邀请发出去没人看。角色缺人超过一天进「需要你」。
- 两个 agent 都来搬：重复项目。按旧位置去重，第二个改为加入。

**要通，需要什么（pd 09-06 23:0x，human：「布置一下让 S9 能通」）**

搬家这件事里，**读旧单据永远归那个 agent**，不归我们：它本来就住在那个项目里，认得自己的任务单、广播、决策台账，或者聊天记录、共享文档。我们不定「旧格式」，只定**写进来的形状**和**人看到的那一步**。这样 S9 与介质无关，也小得多。七件：

| id | 要什么 | 人看到 / 判据 |
|---|---|---|
| **M1 搬家说明书** | 地址返回的说明书加一节「搬家」：只搬在途不搬历史；每条带来源；先放核对卡再收尾；邀请发回旧渠道。给 agent 读，不给人读 | 一个没读过我们仓库的 agent，只凭这一节就能把一支队伍搬进来 |
| **M2 来源与去重** | 任何事件可带 `from`（旧位置：路径、单号、URL、消息 id 都行）。同一个 `from` 再写一次不产生第二条，返回原来那条 | 同一个 agent 跑两次搬家，牌桌上件数不变；两个 agent 同时搬，第二个发现项目已存在改为加入 |
| **M3 显示名** | 任务与决策可带显示名（旧编号）。id 由服务发、永不重排；牌桌显示「T-07 登录超时」，挖层里才是新 id | 旧编号在牌桌上认得出；引用不断链 |
| **M4 核对卡** | 搬完自动给 human 一张卡，措辞见下。这是 human 在整个 S9 里唯一要做的一次点击 | 卡上的四个数字与旧渠道一致 |
| **M5 数字进来即过期** | 导入的事实必须带 `measured_at`（旧记录的时间），且一律标为过期，谁用谁重测（t-051 已有 measured_at，缺的是强制过期） | 没有一条旧数字被当成现行事实用过 |
| **M6 邀请发回旧渠道** | 搬完立刻发，不等 human：agent 把邀请链接写回旧渠道（提交一个文件、发一条广播）。写不了的介质（聊天、口头）退化成给 human 一张卡：「把这个链接发给他们：<链接>」 | 每个原有 agent 在它的下一轮内加入；到不齐的角色在牌桌上缺人 |
| **M7 收尾** | human 点「对」之后，agent 才去旧渠道留最后一条「这里只读」，并记一条事实「迁移完成」。**「对」这个按钮就是动旧渠道的授权**，不点就不动别人的地盘 | 旧渠道之后只有那条「这里只读」 |

**核对卡的措辞与交互（pd 定稿）**

- 种类「问你」。标题：**「搬过来了，对吗？」**
- 正文：「在途 12 件事、7 条现行决定、5 个数字（都标了要重测）、2 个等你答的问题。旧的那边一条没删。」数字来自实际写入条数。
- 主色按钮「对」，描边按钮「有漏」。
- 点「对」→ 卡消失，下方一行「你刚定了：清单对」；服务给第一个节点一条指令：去旧渠道留下「这里只读」，记「迁移完成」。
- 点「有漏」→ 卡消失；服务给第一个节点一条指令：「human 说有漏，回去核对旧单据再补」；「现在」里留一行「等 <角色> 补漏」，补完再问一次。
- 邀请不等这张卡：同伴越早到齐越好。这张卡只授权收尾。

**顺序**：M2 与 M5 是地基（没有它们，导入就是往日志里倒垃圾）；M1 与 M4 是能不能自助的关键；M3 与 M6 让搬过来的东西认得出、同伴找得回；M7 最后。pm 排期与拆任务。

**现状（09-06 22:5x，human 问「S9 现在能用了吗」）**
- 按设计的路（一个地址、一次「对」）**不能**：没有说明书的「搬家」一节；没有导入（任务、决策、数字、问题成批进来）；没有「来自 <旧位置>」字段与按来源去重；没有旧编号进显示名；没有那张「搬过来的是 …对吗？」核对卡。
- 搬家依赖的底座已在生产（eae0b22）：多项目与邀请、任何已声明角色名都能加入、事实分测量时间与记录时间（t-051）。所以一个读得懂通用说明书的 agent **可以手工搬**：建项目、声明角色集、用 API 逐条写入在途任务与现行决策、把邀请链接发回旧渠道。但那是它自己发挥，不是产品保证；核对与去重都没有，漏了也没人说。
- 对 human 的第一个案例（FE / BE / PM / Release manager / UX scanner / QA，agent 已在协作）的建议：**先按「从现在起在这里协作，旧的留在旧处」走**——这是 S8 形状，只差两条说明书缺口；在途的东西不搬，等 S9 做出来再补搬，或干脆让它们在旧处收尾。要真搬在途，S9 至少需要一批：搬家说明书一节、来源字段与去重、显示名、核对卡。
- 现成的验收样本：实战报告那支队伍的 `docs/pm/` 单据（任务单、广播、决策台账、用例登记册、进度板）。用它跑一次搬家，就是 S9 的第一次验收，也是「不在 aTeam 自己身上验」的第一次。

**待 human 拍板** 见文末 Q17、Q18。

## UC-S7 节点来去

**触发** 一个 session 死了或被换掉；一个新平台的 session 加入；项目多了或少了一个角色。

**人看到**
1. 「谁在」按角色列出，每个角色在（绿点，多久前）或缺（灰，「缺人 12 分钟」）。
2. 某个缺人的角色手里有过期未确认的指令时，「需要你」出现一张「请你做」：「qa 已经缺了 20 分钟，手里有 2 条指令。起一个 qa？」按钮「起好了」。
3. 新节点接上后，那张卡消失。

**人做** 通常什么都不做。缺人时起一个 session。

**团队做**
- 节点加入即声明能力事实；离开不用声明，在场靠心跳过期。
- 指令发给角色不发给节点；角色缺人时指令照常排队，过 `ack_by` 升级给人。
- 少角色时规则退化：没有 qa，验收进「需要你」由 human 做；没有 pd，pm 直接把 human 的话变任务。项目声明的角色集决定退化到哪一档。

**完成的标志**
- 任何平台的节点用同一句话加入，十分钟内出现在「谁在」。
- 一个角色缺人，牌桌十分钟内显示；有积压指令时进「需要你」。
- 换掉一个节点，团队其他人没有重复过任何上下文（S6）。
- 只有 pm + dev 的项目也能走完一个「说一句 → 任务 → done → human 验 → 上线」的循环。

**会出错的地方**
- 全队一起死：所有节点共用一个限流池或一台机器，同时暂停，没有任何节点能发现缺人。看门狗必须在池子之外，或至少是新起的 session。
- 两个节点同时持有一个角色，各自 claim、各自 done：身份冲突。今天没有防护。
- 节点自报身份：任何拿到钥匙的人都能说自己是 human。
- 云节点没网、本地节点没部署权限，pm 派错活：能力要是事实，不是假设。

## UC-S8 别人用

**触发** 另一个 product owner 想给自己的项目起一支团队。他不会读这个仓库。

**人看到**
1. 一页「怎么用」，三步：新建牌桌；起 session（每个平台一句话）；每天坐到牌桌前三分钟。页面上有真实的牌桌截图和一条命令。
2. `npx ateam new` 或网页按钮，回来他自己的牌桌地址和钥匙。
3. 他的牌桌，和别人的互不可见。

**人做** 看一页，跑一条命令，然后就是 S0。

**团队做**（这里的团队是 aTeam 自己）
- 托管服务多项目：每个项目自己的日志和钥匙，牌桌地址带项目段。
- 说明书有版本，服务端维护，pd 拥有；升级对所有项目生效，节点下次 join 拿到。
- 自托管是一条命令（一个镜像、一个卷），和托管用同一份工具包。

**完成的标志**
- 没读过源码的人，只凭「怎么用」那一页，一小时内跑起自己的团队并完成一个循环。
- 他的项目与别人隔离：日志、钥匙、牌桌互不可见。
- 我们改说明书，他不用动任何东西。
- 他从头到尾没见过 `packages/`。

**会出错的地方**
- 「怎么用」写成了这个仓库的 README：给贡献者看的，不是给用户看的。
- 一把钥匙管一切：一个项目泄漏就是全部泄漏。
- 说明书里有只对 aTeam 自己项目成立的假设（fly、pnpm、这个仓库的路径）。

**例：一个完全不相关的项目**（human 09-06 提的具体问题）
某人有一个和软件无关的项目，只想用它让自己的几个 agent 沟通协作。
- *接口是什么*：她的 agent 只需要三样输入（地址、钥匙、角色名）和四个动作（拉、确认、说、任务），走 `npx ateam` 或直接 HTTP。`ateam join --me 写手` 拿到说明书就是节点。角色是她项目自己声明的（比如只有「写手」和「审稿」），不用我们的五个。touches 和表面都只是字符串：她的 touches 可以是文档章节，表面可以是「草稿 / 已发布」。
- *要不要独立地址*：要。一个项目一个地址一把钥匙一条日志，托管上是 `…/p/<她的项目>/`，物理隔离，我们的牌桌看不到她的，反之亦然。`npx ateam new` 发的就是这一对，之后我们不参与。
- *要不要牌桌*：要，而且就是同一张。牌桌是从某个项目的日志推导的视图，她的地址上打开的就是她的牌桌，她是她项目里的 `human`。不需要别的界面。
- *边界*：托管意味着运营方在技术上能读她的库；自托管则完全私密。见 Q14。

**现状（09-06 22:45，human 问「是否 ready 挪第一个 S8 案例」）**

# 第二部分 · 团队的用例（A 系列）

owner 不出现。每个用例写：触发、成员做什么、服务器做什么、完成的标志、会出错的地方（实战报告 F）、现状、对应的 replay 断言。

## A1 上岗

**服务的需求** M1 M2 M3 M5 T8。**触发** 一个 session 拿到地址或邀请链接；或一个角色的旧节点死了，新节点来接。
**成员做** 访问地址拿说明书；加入（幂等，同一 agent_id 拿回同一角色同一钥匙）；sync 全量或从快照；先 ack 每条给它的指令；看焦点；接上该接的任务。
**服务器做** 按缺的角色分配；换发节点钥匙；记能力事实；在场从第一次 sync 推导。
**完成的标志** 从拿到地址到第一个正确动作十分钟内；没人给它重复过上下文；牌桌「谁在」十分钟内亮起；日志变长后上岗时间不变长。
**会出错** 说明书随仓库走，新节点按旧规则行动（09-06 pd 上线就发生过）；两个节点同持一个角色；全量回放随日志增长变贵（M5，Q6 暂不做快照）。
**现状（09-06）** 说明书下发（t-039）、地址即工具包（t-040）、多项目（t-041）done；邀请链接换钥匙与按缺分配（t-042）未做；快照没有。**断言** S8 在场。

## A2 一轮

**服务的需求** M2 M4 T2。**触发** 每一轮。
**成员做** 拉 → 先 ack 每条给我的指令 → 看焦点，焦点需要我就切 → 依赖的事实必须有效，否则测一次记下来 → claim 并声明触点 → 做 → done 带证据 → 改变了世界就 `--writes` → 要人现在做的用 tell，理由进 note。
**服务器做** 拒绝引用失效事实的事件（带规则名）；拒绝未声明触点的验收；记录 cursor 即心跳。
**完成的标志** 先 ack 后做事；没有一条事件引用过失效事实；每次拒绝带规则名；被拒次数随时间下降。
**会出错** 把 ack 当同意；触点声明太窄（接缝漏报）；把「代码能跑」当判据满足。
**现状（09-06）** 循环在说明书核心里；拒绝带规则名已成立；被拒次数没有统计。**断言** F3 焦点槽位。

## A3 世界变了

**服务的需求** T1。**触发** 有人部署、迁移、清数据、改配置。
**成员做** 做的人在事件上 `--writes 表面:键`；依赖旧事实的人下一轮发现失效，重测再继续。
**服务器做** 命中 `depends_on` 的事实即失效；到期即过期；被 `refs` 引用时已失效则拒绝。
**完成的标志** 由过期事实导致的返工为零；在错误版本上继续工作的次数为零；每条数字事实都带来源、时间、假设。
**会出错** 假设没写（F6）；基线存成常量（F7）；两个 session 各自重建世界（F8）；搬家搬来的旧数字没标过期（S9）；同一版本记成长短两条 sha 被当成两版（09-06 t-026 真实发生）。
**现状（09-06）** 事实模型与失效规则成立；事实没有「测量时间」与「记录时间」之分（S9 需要）；形状按键声明（t-024）。**断言** F6 F7 F8。

## A4 要人现在做

**服务的需求** T3 T10。**触发** 一个成员要另一个成员现在做一件事。
**成员做** `tell <谁> "<动作>" --ack-by`，280 字，理由另写 note；收件人下一轮先 ack。
**服务器做** 记录送达（被 pull 到）与 ack 时间；过 `ack_by` 未 ack 进逾期；发给 human 的进「需要你」，带默认的到期自动按默认。
**完成的标志** 发出方随时看得到送达了没、ack 了没、排在谁的队列里；逾期十五分钟内升级；行动不被论述淹没。
**会出错** 把放行令埋进长文（F2）；发出方反复发同一条（F1）；逾期只在牌桌上、没人在时没人看（09-06 事故）。
**现状（09-06）** 指令、ack、逾期、默认执行成立；排队位置不可见；升级不带推送。**断言** F1 F2。

## A5 撞车

**服务的需求** T4。**触发** 两件在途工作的触点相交。
**成员做** claim 时把触点写宽；看到接缝就等裁决；后落地的一方合并先落地的再 done。
**服务器做** 触点相交即生成接缝；未解决的接缝挡住双方验收；解决记录带方案；已撤回或已验的任务不再产生接缝。
**完成的标志** 撞车在合入前被拦；每条接缝有主人和结论；「后落地方合并前者」被执行了（done 时检查）。
**会出错** 触点写窄漏报；接缝解决方案写了没执行（09-06 human 手工解冲突一次，t-016/t-037 由此而来）；已撤回的任务反复产生接缝（t-013，t-017 根治）。
**现状（09-06）** 成立，含 done 前的合并检查警告（t-037）；同一 owner 两个任务之间的接缝仍阻塞验收（t-045 待做）。**断言** F4。

## A6 验收

**服务的需求** T5。**触发** 一件工作 done 了。
**成员做** 作者写 done 和证据（能定位产出、逐条对应判据）；验收的人在指定表面上按判据和场景完成标志验，写证据。
**服务器做** 拒绝作者验自己的、判据作者验自己写判据的；验收必须带表面；有未决接缝不能验。
**完成的标志** 自证的交付为零；人可见的交付只有生产表面的验才算；验收记录能回答「谁、在哪、凭什么」。
**会出错** 验收只读交付说明不核仓库（F5）；grep 仓库通过了线上还是旧的（报告 S5）；测试硬编码绝对时间随时钟翻红（09-06 t-022 真实发生，qa 立了判据）。验过之后证据被证不实（09-06 四条 done 证据声称合了某 sha 其实没合）：验收是对表面的一次读数，可被后来的事实推翻——判据仍满足时只发 evidence 更正 note；验收本身靠了不实证据时，非作者在同一表面 verify --fail 推翻，fail 可覆盖 pass、pass 不能覆盖 pass，人看到「仓库验过，后被推翻：…」；不加 reopen，不改历史（pd 09-06 21:5x 决策）。
**现状（09-06）** 成立；pd 评审人可见交付是判据之一（note 留痕）。**断言** F5。

**服务器做** 台账按 supersedes 串起；id 永不重排。
