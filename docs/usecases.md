## UC-S1 开工

**触发** human 打开牌桌。一天里第一次，或任何时候。

**人看到**
1. 「需要你」：只有问他的问题。每条一句话，下面一个选项一个按钮，默认项标出，写明不点的话按哪个；没有选项的问题只有一个「知道了」。
2. 「现在」：焦点一句；线上是哪一版、这一版带来了什么；在途的事按「在做 / 卡住 / 做完了等验 / 验过了还没上线 / 没开始」分组；谁在。
3. 其余全部折叠。首屏没有 id、文件路径、长 sha。

**人做** 逐条点按钮。看完关掉。

**团队做**
- 只有 pd 或 human 把产品问题放进「需要你」，带选项和默认。pm 放进去的只有排期和上线类的问题。
- 带默认的问题到期自动按默认执行，牌桌上显示「已按默认 X 执行（你仍可改）」。
- 牌桌上的一切从日志推导。没有人负责「移卡」。

**完成的标志**
- 「需要你」里每一条都是发给 human 且未回答的问题；回答后它消失，不需要任何人做任何事。
- 每条问题一次点击可答。
- 首屏一屏读完：不超过一屏高度；超出的列表折叠成「还有 N 项」。
- 首屏找不到 id、文件路径、长 sha。
- 从打开到关掉，三分钟。

**会出错的地方**（实战报告）
- F11 看板说谎：一件事早已落地，卡片还挂在「需要你回答」。根治办法是卡片由事实推导，不由记忆推导。
- F10 信噪比衰减：重要的事和例行的事长得一样。根治办法是首屏只放两类东西。
- F3 焦点不在介质里：最要紧的事只在某个人脑子里。焦点槽位是它的答案，但焦点正文现在是给团队写的。

**现状（09-06 07:47）**
- 牌桌 v1（中文、需要你 / 现状 / 折叠）已上线：生产 085624d。human 在上面点过按钮，t-011 在生产验过。
- 牌桌 v2（`docs/board.md`，t-034）frontend 已 done 于 2c98e55，pd 预看与样稿一致，等合并 dev 的指令种类字段（t-036）后正式评审；human 已定第 4 批上线等 v2 一起。
- 「这一版带来了什么」（t-026）已做，但「自上一版 X 以来」显示的是当前 sha，已让 frontend 改。
- 焦点正文仍是团队话（Q1 已定不分两句）。

**已拍板** Q1：焦点不分两句，保持一条；pm 写焦点时顾及 human 在读。

## UC-S2 需求变了

**触发** human 说一句话：想要什么、不要什么、改什么。

**人看到**
1. 这句话变成了一条场景需求（pd 的决策 note）和一个或几个任务，牌桌「在途」里出现它们。
2. 受影响的在途工作被标出：谁手里的东西要变。
3. 之后再没有人来问他「你的意思是不是……」，除非是一个新的产品问题，而且带选项和默认。

**人做** 说一句。回答后续的选项题。

**团队做**
- pd 把这句话写成场景需求：human 会看到什么、做什么、为什么；注明取代了哪条旧决策。
- pm 把需求变成任务，每个任务写明服务的场景 id 和它来自哪条需求 note；受影响的在途任务由 pm 用指令通知持有者，持有者 ack。
- 每个 session 下一次 sync 看到指令并 ack。全队对齐的标志是所有相关指令都 ack 了。

**完成的标志**
- 一句话到任务出现在牌桌上，五分钟以内。
- 受影响的在途任务被标出并且持有者已 ack。
- human 不需要第二次解释：同一件事不会再出现在「需要你」里，除非换了一个问题。
- 每个任务能回指到它来自的需求 note。

**会出错的地方**
- F2 行动被论述淹没：需求变更埋在一段长文里，做的人没看见。指令 280 字上限和必须 ack 是它的答案。
- F8 相反的信念：两个 session 对「现在要什么」持相反看法。需求作为决策 note 有唯一最新版本。
- F9 重排断链：需求改了名，引用它的任务说的不再是同一件事。id 永不重排。

**现状（09-06 07:47）**
- 「说一句」（t-031）frontend 已 done，随 v2 一起上线；去向（已收到 → 需求 → 任务）靠 note 的 refs 推导。
- 今天 human 的话仍全部经 pd session 转录（Q1–Q14、牌桌反馈、边界场景）。
- 任务开始写场景 id 了（t-026 起）。任务回指需求 note 还没有字段，写在标题或 note 里。
- 「受影响的在途工作」没有机制：接缝只看代码触点，需求变更不产生接缝。今天靠 pm 手工发指令。

**已拍板** Q2：两者都要，而且目标是 human 之后不需要进任何 session，只用牌桌就能完整参与（写进了 product.md 的目标）。场景需求「牌桌上说一句」已写成决策 01M1TSF3QPY86YQD73RKPTMTBH，交 pm 排期：输入框在「需要你」下方，说一句进日志，下方「你说过的」列表显示每句的去向（已收到 → 已成为需求 → 已成为任务）。

## UC-S3 上线

**触发** 一批任务在仓库表面验过，pm 组成一个上线批次。

**人看到**
1. 「需要你」里一条问题：「上线这一版？」下面列出这一版包含的任务标题、每个任务谁验过、在哪个表面验的；一个「上线」按钮，一个「不」。
2. 点了之后，牌桌「线上」变成新版本，列出这一版带来的东西，以及生产上验过没有。

**人做** 看一眼，点一下。

**团队做**
- pm 把批次写成一条给 human 的问题：包含什么、谁验过、在哪个表面。
- 部署由一个动作触发（今天是合并到集成分支并推 `production`，CI 部署）。部署完成后记录 `production:deployed.sha` 事实，这一条让所有依赖旧版本的事实失效。
- qa 在生产表面重验人可见的交付。仓库上验过的不算线上验过。

**完成的标志**
- 上线前 human 在牌桌上看得到：这一版包含哪些任务、谁验过、在哪个表面验的。
- 部署是一次点击（或至多一条命令）。
- 部署后牌桌自动显示新版本和这一版带来的任务，不需要任何人手工更新。
- 人可见的交付只有在生产表面验过才显示为「线上验过」。

**会出错的地方**
- S5 表面混淆：grep 仓库通过了，线上还是旧文案，中间隔着一次部署。表面标签是它的答案。
- F5 验收只读交付说明不核仓库。验证必须由不是作者的人、在命名的表面上做。
- F7 事实过期：部署后旧的 deployed.sha 仍被引用。`writes` 让它失效。

**现状（09-06 07:47）**
- 第 3 批已上线（085624d）：仍是 human 按 pm 的「请你做」手工合并推 `production`，但这条请求已经出现在牌桌「需要你」里，human 点「做好了」。
- 牌桌「线上」已显示「这一版带来了什么」（t-026），上一版 sha 的显示有一处错，在改。
- 第 4 批 human 已定等牌桌 v2 一起上。

**已拍板** Q3：S3 分两阶段。**现阶段持续自动发布**：合到集成分支推 `production` 即部署，不需要人点；牌桌的责任是正确显示线上是哪一版、这一版带来了什么（t-026 是第一步）。**后一阶段**：积累一些 feature 后，由人在牌桌上手动点发布；到那时才需要「上线这一版？」的问题和「版本」对象。上面「人看到」的第 1 条属于后一阶段。

## UC-S4 出事了

**触发** human 发现线上坏了，说「这个坏了」加一句描述。

**人看到**
1. 「在途」里出现一条标 S4 的任务，在做。
2. 修好后「需要你」里一条：「已修好：<证据>，关闭？」证据是他能自己核的东西：一条生产上的读数、一个截图、一段线上输出。
3. 点「关闭」。

**人做** 说一句。看证据，点一下。

**团队做**
- pd 把这句话写成一条 S4 场景需求（human 看到了什么、期望什么）。pm 建任务，判据里必须有「在生产表面复现」和「在生产表面验过」。
- dev 先复现（一条失败的读数或失败的 verify 记录在生产表面），再修，再 done。
- qa 在生产表面验，证据写成 human 看得懂的形式。
- 关闭由 human 做，不由修的人做。

**完成的标志**
- 有一条生产表面的记录证明它坏过（复现），有一条证明它好了（验证）。
- human 只看证据，不看代码，不看讨论。
- human 不需要第二次描述。

**会出错的地方**
- 「done」不等于修好：实战报告里那次守卫测试从未推上远端。done 是声明，verify 才是判定。
- 验在仓库不验线上。表面标签。
- 证据是结论不是证据：「已修复」四个字不算。

**现状（09-06 07:12）**
- 没有单独的故障对象。任务加一条生产表面的失败 verify 记录可以表达「坏了」，但没有人这样用过。
- 入口和 S2 一样是 pd session。
- 证据展示给人的形式没有定：今天的证据是给 qa 看的 sha 和命令输出。

**已拍板** Q4：不做新对象。用任务标 S4，判据固定含「生产表面复现」和「生产表面验过」；统计上 S4 任务可以单列（故障数、修复时长），但牌桌上对人和别的任务没有区别。

## UC-S5 回头看

**触发** human 问「为什么这样改」「这个什么时候上的」「谁验的」。

**人看到** 从线上版本出发：这一版包含的任务 → 每个任务服务的场景、来自的需求 note、判据 → 谁做的、谁在哪个表面验的、验的证据 → 相关决策和它取代的旧决策。

**人做** 点三下以内。

**团队做**
- 每个任务写明场景 id 和来自的需求 note。
- 决策只以 note 存在，改决策用 supersedes，不改历史。
- done 的证据带 sha；部署记录带 sha。

**完成的标志**
- 任何线上的改动，三跳以内追到需求、决策、验证。
- 决策台账里没有被编辑过的历史，只有新条目取代旧条目。

**会出错的地方**
- F9 重排断链：引用是字符串不是链接。id 永不重排是它的答案。
- F6 数字带着看不见的前提：追溯到的事实要带假设和有效期。

**现状（09-06 07:12）**
- `task show` 有判据、证据、验证记录、挂在任务上的 note；决策台账有 supersedes。
- 从 sha 反查任务做不到：证据是自由文本。牌桌上没有「版本」这个对象。
- 任务回指需求 note 还没有字段。

**已拍板** Q5：现在没有发布版本的概念，逐渐引入。S5 暂靠日志和 `task show` 追溯；「版本」对象随 S3 后一阶段引入，那时牌桌折叠区加「版本」列表。

## UC-S6 换人

**触发** human 起一个新 session，第一句「协作模式，你是 X」。

**人看到** 新 session 几分钟后开始正确行动：ack 了给它的指令，看了焦点，接上了该接的任务，没有问 human 任何「现在是什么情况」。

**人做** 一句话。

**团队做**
- 新 session 读 CLAUDE.md、`docs/`、全量 sync、牌桌。
- 团队其他人不需要给它重复上下文。

**完成的标志**
- 新 session 不需要 human 交代任何事。
- 团队其他人没有为它重复过上下文。
- 从起 session 到第一个正确动作（ack 或 claim），十分钟以内。

**会出错的地方**
- 角色变了但 CLAUDE.md 没跟上：新 session 按旧规则行动。今天 pd 上线后十分钟内角色定义改了一次，pd 凭旧定义设了一次焦点。

- 没有「当前状态摘要」这种东西；新 session 靠读全量日志重建。

**已拍板** Q6：暂不做交接摘要。

## UC-S0 起项目

**触发** human 有一个新想法或一个新仓库，手里有一个 agent（任何平台的一个 session）。

**human 的全部输入**：一个地址。对自己的 agent 说「用 https://ateam.fly.dev 起一个项目」。之后最多再说一句「这个项目是什么」，而且是在牌桌上说。

**人看到**
1. 几分钟后 agent 回一句：「牌桌在这里：<地址>」。
2. 打开牌桌，「需要你」里只有一张卡：「这个项目是什么？说一句。」下面一行「要更多 agent，把这个链接给它们：<邀请链接>」。
3. 说完，焦点出现，在途出现第一批任务；他把邀请链接丢给别的 session（Codex、本地、云，都是同一个链接），「谁在」一个个亮起来。

**人做** 一个地址，一句话，转发一个链接。不改文件，不见钥匙。

**agent 和服务自主完成的**
- **地址即工具包**：agent 访问那个地址，拿到的是写给「还没加入的 agent」的说明书：怎么新建项目、怎么加入、下一步做什么。纯 HTTP 就能完成，CLI 只是省事。
- agent 新建项目，拿到项目地址、管理钥匙、邀请链接；把钥匙写进自己的环境，不经过人。
- 第一个节点默认当 pm：设焦点「等 human 说这个项目是什么」，放那张唯一的卡，把牌桌地址回给人。
- 之后每个拿到邀请链接的 agent：访问链接拿到说明书，服务按「缺哪个角色」分配角色（可改），换成自己的节点钥匙，sync、ack，开始干活。
- human 说了那句话后，pd（若有）写 product.md v0，pm 建第一批任务；若只有 pm + dev，pm 直接建任务。
- 仓库若有，agent 自己写存根（`CLAUDE.md` / `AGENTS.md` / `docs/ateam.md`）；若没有，仓库地址等有了再作为事实记进来。

**完成的标志**
- human 的输入不超过：一个地址、一句话、转发一个链接。
- 从给出地址到第一个节点在牌桌上出现，五分钟；到团队在做他那句话，十五分钟。
- 钥匙从未出现在任何对话里；human 没有手改任何文件。
- 任何平台的 agent 拿同一个链接都能加入，只靠地址返回的说明书，不靠我们的仓库。
- 同一个 agent 起两次不会出现两个节点：加入是幂等的（S6）。

**会出错的地方**
- 说明书随仓库走：agent 得先 clone 我们的仓库才知道怎么加入。地址必须自描述。
- 钥匙靠人在聊天里传：泄漏且无法撤销。邀请链接短时有效、换成节点钥匙。
- 第一个 agent 不知道自己该当谁：默认角色由服务给，不由人交代。
- 角色定义在不同项目间漂移：说明书核心只有一份，由服务下发。

**现状（09-06 07:55）**
- 地址 `ateam.fly.dev` 返回的是本项目的牌桌，不是给陌生 agent 的说明书。没有「新建项目」，没有邀请链接，没有角色分配。
- 只有这一个项目：「一个项目、一条日志、一把钥匙」，`X-Actor` 自报身份。
- CLI 未发布；说明书住在本仓库 CLAUDE.md，混着本项目档案（见 `docs/self.md`）。
- 起这个项目本身花了 human 一个上午的手工配置。
- 第一个真正的验收：在一个不是 aTeam 的项目上，从一个地址起一支团队。

**待 human 拍板** 见文末 Q7–Q16。

## UC-S7 节点来去

**触发** 一个 session 死了或被换掉；一个新平台的 session 加入；项目多了或少了一个角色。

**人看到**
1. 「谁在」按角色列出，每个角色在（绿点，多久前）或缺（灰，「缺人 12 分钟」）。
2. 某个缺人的角色手里有过期未确认的指令时，「需要你」出现一张「请你做」：「qa 已经缺了 20 分钟，手里有 2 条指令。起一个 qa？」按钮「起好了」。
3. 新节点接上后，那张卡消失。

**人做** 通常什么都不做。缺人时起一个 session。

**团队做**
- 节点加入即声明能力事实；离开不用声明，在场靠心跳过期。
- 指令发给角色不发给节点；角色缺人时指令照常排队，过 `ack_by` 升级给人。
- 少角色时规则退化：没有 qa，验收进「需要你」由 human 做；没有 pd，pm 直接把 human 的话变任务。项目声明的角色集决定退化到哪一档。

**完成的标志**
- 任何平台的节点用同一句话加入，十分钟内出现在「谁在」。
- 一个角色缺人，牌桌十分钟内显示；有积压指令时进「需要你」。
- 换掉一个节点，团队其他人没有重复过任何上下文（S6）。
- 只有 pm + dev 的项目也能走完一个「说一句 → 任务 → done → human 验 → 上线」的循环。

**会出错的地方**
- 两个节点同时持有一个角色，各自 claim、各自 done：身份冲突。今天没有防护。
- 节点自报身份：任何拿到钥匙的人都能说自己是 human。
- 云节点没网、本地节点没部署权限，pm 派错活：能力要是事实，不是假设。

**现状（09-06 07:40）**
- 在场靠 cursor 时间推导，有 idle 秒数，没有「缺」的概念，没有升级。
- 没有能力事实。没有角色集声明；五个角色写死在 CLAUDE.md 里。
- 今天 pd 的加入就是一次 S7：可行，但靠 human 亲手改 CLAUDE.md 加角色。

## UC-S8 别人用

**触发** 另一个 product owner 想给自己的项目起一支团队。他不会读这个仓库。

**人看到**
1. 一页「怎么用」，三步：新建牌桌；起 session（每个平台一句话）；每天坐到牌桌前三分钟。页面上有真实的牌桌截图和一条命令。
2. `npx ateam new` 或网页按钮，回来他自己的牌桌地址和钥匙。
3. 他的牌桌，和别人的互不可见。

**人做** 看一页，跑一条命令，然后就是 S0。

**团队做**（这里的团队是 aTeam 自己）
- 托管服务多项目：每个项目自己的日志和钥匙，牌桌地址带项目段。
- 说明书有版本，服务端维护，pd 拥有；升级对所有项目生效，节点下次 join 拿到。
- 自托管是一条命令（一个镜像、一个卷），和托管用同一份工具包。

**完成的标志**
- 没读过源码的人，只凭「怎么用」那一页，一小时内跑起自己的团队并完成一个循环。
- 他的项目与别人隔离：日志、钥匙、牌桌互不可见。
- 我们改说明书，他不用动任何东西。
- 他从头到尾没见过 `packages/`。

**会出错的地方**
- 「怎么用」写成了这个仓库的 README：给贡献者看的，不是给用户看的。
- 一把钥匙管一切：一个项目泄漏就是全部泄漏。
- 说明书里有只对 aTeam 自己项目成立的假设（fly、pnpm、这个仓库的路径）。

**例：一个完全不相关的项目**（human 09-06 提的具体问题）
某人有一个和软件无关的项目，只想用它让自己的几个 agent 沟通协作。
- *接口是什么*：她的 agent 只需要三样输入（地址、钥匙、角色名）和四个动作（拉、确认、说、任务），走 `npx ateam` 或直接 HTTP。`ateam join --me 写手` 拿到说明书就是节点。角色是她项目自己声明的（比如只有「写手」和「审稿」），不用我们的五个。touches 和表面都只是字符串：她的 touches 可以是文档章节，表面可以是「草稿 / 已发布」。
- *要不要独立地址*：要。一个项目一个地址一把钥匙一条日志，托管上是 `…/p/<她的项目>/`，物理隔离，我们的牌桌看不到她的，反之亦然。`npx ateam new` 发的就是这一对，之后我们不参与。
- *要不要牌桌*：要，而且就是同一张。牌桌是从某个项目的日志推导的视图，她的地址上打开的就是她的牌桌，她是她项目里的 `human`。不需要别的界面。
- *边界*：托管意味着运营方在技术上能读她的库；自托管则完全私密。见 Q14。

**现状（09-06 07:40）**
- 单项目。没有「新建」。没有「怎么用」。README 是给贡献者的。
- 说明书里满是本项目的假设（`./bin/ateam`、`pnpm build`、`./bin/deploy`、fly）。
