# aTeam · 职责与系统要求

> v0 草案，2026-09-06。**pd 拥有此文档。** 比 `docs/product.md` 低一层：product.md 讲两个用户和他们的需求（O/T/M）与用例（S/A）；这份讲**一项项工作职责**，以及每项职责对人、对持有它的 agent、对协作方 agent、对通讯机制与牌桌各提什么要求。改动先 `note --decision`，再改这里。

## 原则

**角色会重组，职责不会消失。** 一个项目怎么划角色是它自己的事：软件项目常用 pd / pm / dev / frontend / qa，一个写作项目可能只有「写手」和「审稿」，一个最小团队只有两个节点。但不管怎么划，「谁定验收标准」「谁在指定表面上判定」「谁测量世界」这些职责都还在，只是落在不同的身份上，或者退化给 owner，或者由服务替代。

所以这份文档的单位是职责（R1…），不是角色。三个推论：

1. **角色 = 一组职责。** 项目声明角色集时，每个角色就是本文若干项职责的打包。默认五角色的打包见文末；最小团队（两个节点）和非软件项目的打包也在文末。
2. **说明书按职责拼装。** 说明书 = 通用核心 + 该角色持有的每项职责的「持有者需要知道」段 + 项目档案。这样任意角色名（writer、审稿、运维）都能拿到一份对的说明书，不必为每个可能的角色名预写一份。
3. **三方分离是职责之间的约束，不是角色之间的。** 「定判据（R3）、做（R5）、验收（R6）不能是同一身份」在任何打包下都成立；打包时如果两项落到同一角色，第三项必须落到别处，落不到就退化给 owner，服务器据此判定。

每项职责按同一个模板写：

- **输出**：它产生什么。
- **今天 / 最小团队 / 非软件项目**：今天本项目谁持有；只有两个节点时谁持有；一个写作类项目里它长什么样。
- **owner 需要知道**：牌桌上该给人看什么。
- **持有者需要知道**：拿到这项职责的 agent 需要哪些输入。这一段就是说明书里该角色的那一节。
- **协作方需要知道**：其他 agent 需要从这项职责得到什么。
- **通讯与牌桌的特殊要求**：哪些必须是指令（同步、需 ack）、哪些是事实、哪些是 note；牌桌上放哪、怎么放。
- **现状与缺口**（09-06）。

## 方向

### R1 定方向与优先级

**输出** 焦点（一句）；批次顺序；被推迟的事及理由。
**今天 / 最小团队 / 非软件** pm / pm / 主编或负责人。
**owner 需要知道** 焦点是什么、为什么是它（一句话）、什么时候变的；焦点之外被推迟了什么（挖层）。不需要知道排期细节。
**持有者需要知道** owner 最近说的每一句及其去向；在途任务全集与状态；谁在听、谁缺；未决接缝；等验的交付；线上是哪一版；协作报告的发现。
**协作方需要知道** 焦点变了（立刻，下一轮必读）；自己手上的活在不在焦点里；被叫停时停到什么状态（done 还是搁置）。
**通讯与牌桌** 焦点是一个槽位事实，变更即广播（每个成员下一轮必读）；由焦点变更引起的「停手」必须是指令（需 ack）；牌桌首屏只显示焦点一句，正文要能被 owner 读懂。
**现状与缺口** 焦点槽位成立（F3）；「被推迟的事」没有列表；焦点正文常是团队话。

### R2 把人的话变成要求

**输出** 场景需求 note（引用原话）；产品文档；人可见之物的措辞与交互定稿；给 owner 的产品问题（带选项、默认）；评审结论。
**今天 / 最小团队 / 非软件** pd / pm 兼任 / 编辑。
**owner 需要知道** 他说的每一句变成了什么（已收到 → 需求 → 任务 → 上线）；哪些问题在等他，默认是什么；哪些默认已生效、他还能改。
**持有者需要知道** 原话原文与时间；现行决策及其取代链；跑起来的产品（真实表面，不是代码）；挂在任务上的评审请求；实战里哪个场景没被服务到（R12 的观察）。
**协作方需要知道** 需求的唯一现行版本；措辞定稿后不得自改；哪些交付 done 前要经此职责评审。
**通讯与牌桌** 「说一句」进日志后靠 refs 连成去向链，牌桌显示每句的去向；决策用 note --decision + supersedes；评审请求挂在任务上（note --task），不用指令催；产品问题只能由此职责持有者或 owner 本人放进「需要你」，且必须带选项和默认。
**现状与缺口** 去向链、评审留痕、决策台账成立；「说一句」待上线，今天原话经 pd session 转录；评审前分支头是否还在动没有提示（09-06 pd 评审了过时的头一次）。

### R3 定验收标准

**输出** 判据：可判定的句子，带场景 id 与需求 id；判据模板；从失败中学到的通用判据。
**今天 / 最小团队 / 非软件** pm（pd 可补） / pm，但由 owner 验 / 编辑定稿标准。
**owner 需要知道** 不需要看判据本身；需要知道「做完」是被谁、按什么、在哪验的（挖层一行）。
**持有者需要知道** 场景的完成标志；需求 id；判据库（R6 从失败里学到的：绝对时间戳、接缝合并检查、数据侧先于页面侧）；哪些判据要写「在生产表面」。
**协作方需要知道** 判据在动手前定稿；改判据只能追加且有留痕；对判据有异议走 concern，不自行改。
**通讯与牌桌** 判据是任务的结构化字段，不是聊天；追加判据是事件（criteria add）；三方分离由服务器判定；判据库要能被检索，不只是散落的 note。
**现状与缺口** 成立；判据库只是 note，没有检索入口；模板没有固化成工具。

### R15 拍板

**输出** 决定（点一下）；政策（到期按默认、谁能推生产、什么算上线）。
**今天 / 最小团队 / 非软件** owner / owner / owner。不可委托给 agent，但可以给默认。
**owner 需要知道** 问题、选项、默认、到期时间；他刚定了什么；默认替他定了什么、能不能改。
**持有者需要知道**（= owner）只需要牌桌。
**协作方需要知道** owner 的 ack 不等于某个角色的 ack；默认生效有留痕；哪些事是 owner 保留的（产品范围），不可替他决定。
**通讯与牌桌** 「问你」卡：一个选项一个按钮，默认主色；到期按默认并显示「已按默认 X 执行（你仍可改）」；「你刚定了」一行。
**现状与缺口** 成立。旁观者看到的「需要你」要看起来不像在叫他（未做）。

## 工作

### R4 拆分与派活

**输出** 任务（标题、判据、场景/需求 id）；指派；解除阻塞；数据侧 / 页面侧拆分；接口约定先行。
**今天 / 最小团队 / 非软件** pm / pm / 主编。
**owner 需要知道** 在途有几件、几件卡住、卡住的原因一行；不需要知道谁做。
**持有者需要知道** 谁在听、谁空闲、每人手上几件；能力事实（能不能推生产、有没有网）；接口约定 note 出现了没有；未决接缝；被叫停的人停在哪。
**协作方需要知道** 接到的活的判据与接口；什么时候可以 claim（接口 note 出现后）；被换活先 ack 再停。
**通讯与牌桌** 指派与换活用指令（需 ack）；能力与在场是事实；接口约定是 note 且可被 refs；牌桌「在途」计数条与卡住原因；同一收件人五分钟内不发第二条指令除非是取消（pm 报告发现三）。
**现状与缺口** 成立；能力事实未做；「接口 note 先于页面任务」是判据模板不是规则；pm 18% 的指令十分钟内被自己更正。

### R5 做

**输出** 产出（代码、文稿、设计、任何东西）+ done 证据（能定位产出、逐条对应判据）。
**今天 / 最小团队 / 非软件** dev、frontend / dev / 写手。
**owner 需要知道** 在做什么（标题、负责人）；不看过程。
**持有者需要知道** 判据与场景完成标志；说明书；项目档案（产出交到哪、怎么合并）；触点要诚实写宽；依赖的事实是否有效；接缝结论（谁合谁）；done 前本地测试要过（09-06 一次冲突标记被推上远端）。
**协作方需要知道** 它的触点（避免撞车）；它 done 的证据与位置（后落地方合并）；它 `writes` 了什么（事实失效）。
**通讯与牌桌** claim 带结构化触点；done 带证据；`writes` 让事实失效；不需要广播进度，进度就是任务状态。
**现状与缺口** 成立；done 时若证据位置上的测试不过应警告（frontend friction，未做）。

### R8 裁决接缝与集成

**输出** 接缝结论（谁合谁、边界在哪）；集成批次；集成分支头。
**今天 / 最小团队 / 非软件** pm（34 次里 32 次手工） / 规则自动 + 后落地方 / 主编合稿。
**owner 需要知道** 不需要。挖层显示未决接缝数。
**持有者需要知道** 触点重叠在哪；双方状态与谁先 done；分支头与合并方向；哪些接缝是同一 owner 的（不该阻塞）。
**协作方需要知道** 结论；done 前的合并检查结果；自己是不是后落地方。
**通讯与牌桌** 接缝是一等对象，结论结构化；后落地方合并的检查在 done 时自动（t-037）；同一 owner 的接缝不阻塞（t-045）；已撤回、已验的任务不产生接缝（t-009、t-017）。
**现状与缺口** 规则在收敛，pm 的手工成本正在下降；接缝结论「谁合谁」还没有默认规则（后落地方合并是规范不是规则）。

## 判定

### R6 验收

**输出** 在指定表面上的 pass / fail 记录，带证据；从失败里学到的判据（note）；验收时测到的事实。
**今天 / 最小团队 / 非软件** qa / owner（服务器规则退化：无 qa 时验收进「需要你」） / 审稿人在「已发布」表面上看。
**owner 需要知道**
- 哪些东西验过了、在哪个表面、结论一行；人可见的交付只有生产表面的验才显示为「线上验过」。
- FAIL 的原因一句话（不是日志）。
- 缺 qa 时，哪些交付在等他验，判据是什么，证据在哪：这是一张「请你做」卡。
- 证据要是他自己能核的形式：一条生产上的读数、一个截图、一段线上输出；不是 sha 和命令输出（S4、O5）。
**持有者需要知道**
- 判据全文 + 场景的完成标志（两者都要对照）。
- 被验对象的准确位置：分支、sha、表面；作者的 done 证据。
- 自己不能验的：自己写了判据的任务（服务器会拒）。
- 有没有未决接缝（有则被拒，要把接缝 id 与 owner 指出来交给 R8）。
- 哪些表面算数：人可见的只认生产；仓库验过不等于线上验过（报告 S5）。
- 陷阱清单：绝对时间戳随时钟翻红；grep 仓库通过但线上未部署；「代码能跑」不等于「判据满足」；测试命令的退出码被管道吞掉。
- 上一次 FAIL 的原因（重验时先看它消没消）。
**协作方需要知道**
- 作者：结果与原因（FAIL 要能立刻改）；被拒时的规则名。
- R4 / R8：哪些交付在等验、哪些被接缝挡住（排批用）。
- R3：从失败里学到的新判据（采纳进判据库）。
- R9：哪些在仓库验过可以进批次；部署后哪些要在生产上重验。
**通讯与牌桌的特殊要求**
- verify 是结构化事件（表面、pass、证据），不是聊天；不带表面的验收无效。
- FAIL 应自动通知作者（今天靠 qa 手工 tell），并把任务状态变为「验收未过，待修」。
- 牌桌「在途」有「做完了，等验」和「验过了，还没上线」两组；部署后「线上」只列在生产上验过的。
- 被接缝挡住时，输出里带接缝 id 与它的 owner，而不是「被拒」两个字。
- 缺 qa 时，服务器把待验交付作为「请你做」放进「需要你」，附判据与证据链接。
- 证据格式：给 owner 的证据和给团队的证据是两层，牌桌只显示前者。
**现状与缺口** verify 规则、三方分离、表面成立（F5）；FAIL → 作者通知靠手工；缺 qa 的退化未实现（没有角色集声明）；证据面向 qa 不面向 owner；判据库无检索；接缝被拒时的输出已带接缝信息。

### R7 测量世界

**输出** 事实：值、表面、时间、方法、假设、有效期、依赖。
**今天 / 最小团队 / 非软件** 谁用谁测（qa、dev、owner） / 同 / 同（发布状态、稿件字数、审稿轮次）。
**owner 需要知道** 线上是哪一版、谁在什么时候核对的；关键数字是否过期（灰）。
**持有者需要知道** 键的形状；依赖哪些表面:键；方法必须写；有效期的选法（行为判据长期有效，数值基线用一次就该重取，报告 S9）；搬来的数字带的是当时的时间。
**协作方需要知道** 引用前检查是否有效；失效后重测的责任归引用者；`writes` 会让谁失效。
**通讯与牌桌** 事实是结构化事件；失效与过期自动；引用失效事实被拒（带规则名）；牌桌「线上」一行 + 挖层事实表，过期的灰显。
**现状与缺口** 成立（F6 F7 F8）；缺测量时间与记录时间之分（S9 要）；同一版本长短 sha 被当两版（已修）。

### R12 看着跑起来的东西说哪里不对

**输出** 观察 note（哪个场景其实没被服务到；线上哪里坏了）；S4 的「这个坏了」也是它。
**今天 / 最小团队 / 非软件** pd 巡查、owner 自己 / owner / 读者或编辑试读。design-v0.1 里的 User Simulator agent 就是这项职责的专职持有者。
**owner 需要知道** 他报的「坏了」变成了什么（同 R2 的去向链）。
**持有者需要知道** 真实表面的访问方式；场景完成标志；这一版带来了什么（对照）；上次观察的去向。
**协作方需要知道** 观察不是需求：要经 R2 变成需求、经 R4 变成任务；观察带证据（截图、读数）。
**通讯与牌桌** 观察 = note（不承载动作），带表面与证据；由 R2 决定是否成需求；不进「需要你」。
**现状与缺口** pd 手工巡查（09-06 用生产日志渲染截图）；无 User Simulator；观察的去向链未单独显示。

## 变化

### R9 发布与改变世界

**输出** 部署 / 迁移 / 清数据；`writes`；部署后的 `deployed` 事实；（第二阶段）上线按钮背后的动作。
**今天 / 最小团队 / 非软件** 团队自己（Q20 = A，09-06） / dev / 发布稿件的人。
**owner 需要知道** 线上换了版；这一版带来了什么；（第二阶段）上线这一版？一键。
**持有者需要知道** 批次内容与每件的验收状态；部署方法（项目档案）；要 `writes` 哪些键；CI 结果；部署后记事实；**自己有没有推的许可和凭据**（两者都要，缺一不推；这是节点加入时该记的能力事实，09-06 全队因此卡住一次）。
**协作方需要知道** 部署了（依赖旧版本的事实失效、重测）；哪些交付要在生产上重验（R6）。
**通讯与牌桌** `writes` 结构化；`deployed` 事实由部署者记（最好由 CI 自动记）；牌桌「线上」行自动更新；owner 不在部署路径上。
**现状与缺口** Q20 = A 已定但暂不能执行：本运行时云节点被钉在自己分支，没有任何节点能推 production，human 在牌桌上三选一（15:03）；CI 自动记 deployed 事实未做；`ateam release --deploy`（t-052）已 done 未验。

### R10 决策台账

**输出** 决策 note；取代链；现行决策集合。
**今天 / 最小团队 / 非软件** 人人（pd 产品、pm 排期、owner 拍板） / 同 / 同。
**owner 需要知道** 他拍过什么、默认替他定了什么、哪些决定被推翻。
**持有者需要知道** 现行决策集合；一件事已有的决策（避免两个人各写一条）。
**协作方需要知道** 决定唯一最新版；引用 id 不引用文字。
**通讯与牌桌** note --decision + supersedes；牌桌「已定」与「你刚定了」；缺一个「现行决策」视图。
**现状与缺口** 台账成立（41 条，9 条被取代）；无现行决策视图；09-06 pd 与 pm 对同一事各写一条，事后互指。

## 团队自身

### R11 改进工具与规则

**输出** tooling 任务；规则改动；协议复盘（哪些规则触发过、哪些被绕过）。
**今天 / 最小团队 / 非软件** pm 建、dev 做 / dev / 同。
**owner 需要知道** 不需要；只需 tooling 不压过场景。
**持有者需要知道** friction 汇总；规则触发统计；overfit 清单（不把本项目约定固化进平台）。
**协作方需要知道** friction 只记不争；被拒读规则名。
**通讯与牌桌** friction note 前缀；复盘写成文档不进牌桌。
**现状与缺口** 成立（38 条 friction）；规则触发统计未做。

### R13 报告协作健康

**输出** 定期协作报告：节奏、指令延迟、返工、摩擦、人的负担、结构性发现、给 R2 的问题。

## 分配预警（平台提供）

human 09-06 的第二条：职责分配不合理是常见错误，可以预警。五种模式，每种写它长什么样、今天的例子、怎么从声明或日志里看出来、提示词。都是软预警，不阻塞；只有三方分离由服务器在事件时拒绝。

| 模式 | 长什么样 | 今天的例子 | 怎么检测 | 提示词 |
|---|---|---|---|---|
| **重叠** | 同一职责两个角色都持有，没有分界规则；同一件事出现两条互不取代的决策；同一收件人短时间收到两个发件人内容相近的指令 | pm 与 pd 对「起好了」各写一条决策，事后互指 | 静态：一项职责在两个角色的集合里且没有分界说明。运行时：十分钟内两条决策 note 引用同一任务且不互相 supersede；同一收件人五分钟内收到两条不同发件人、正文相似度高的指令 | 「R2 由 pd 和 pm 同时持有，没有分界。建议：一个持有，另一个只提 concern。」 |
| **低效** | 一项职责的持有者是瓶颈：本该由规则或服务做的事靠人手工；一个角色的 ack 延迟远高于其他人；等它验收的队列持续增长 | 34 次接缝 32 次 pm 手工；17 次验收被接缝挡回来找 pm | 运行时：某类事件（seam 解决、criteria add）由同一角色手工完成的比例；按角色的 ack 延迟 p90 与队列深度；等验任务数随时间不降 | 「接缝 94% 由 pm 手工解决。建议：把『后落地方合并』做成规则（已做 t-037）。」 |
| **无效上下文移交** | 一条本来连续的职责链被切到几个角色手里，每一刀都逼下一个角色重新获取上一个角色已有的上下文：重新读、重新问、重新转述。逐字转发是它最便宜的症状，重新推导是最贵的。切断职责链只有一个正当理由——独立审核（R5 与 R6、R3 与 R6 之间的那一刀）；其余的切断，要么产物把上下文带过去（结构化需求、判据引用需求 id），要么就是无效移交 | 牌桌 v2：pd 决策 → pm 写判据（逐条转述 board.md）→ frontend 实现 → pd 评审 → pm 补判据 → qa 验，五个角色六次移交，同一上下文重讲四遍；「起好了」的语义在 pd 与 pm 之间来回两次；human 的语言规则由 pm 逐字转发三条（退化情形） | 静态：天然连续的链（R12→R2→R3→R4、R8→R9、R6→R3 判据回流）被切到不同角色，而中间产物不是结构化引用（判据不 refs 需求、任务不 refs 决策）。运行时：一个任务的链上不同角色数与移交次数；转述型产物（一个角色的 note 或判据大段复述另一角色的 note）；同一任务的评审来回轮数；指令正文与十分钟内另一条相似且发件人不同（转发） | 「t-034 的链经过 5 个角色 6 次移交，其中 2 次是转述。建议：R2 直接产出判据草案（pd 补判据已允许），pm 只加场景 id 与排期；或让判据 refs 需求 note，frontend 读需求不读转述。」 |
| **打破独立审核** | 判据作者 = 实现者；验收者 = 作者；打包时 R3、R5、R6 落在同一角色而没有退化到 owner；pd 补了判据后又去评审同一交付 | dev 给自己写判据建了 t-038（pm 撤回）；写作项目里审稿既定标准又验收 | 静态：某角色的集合同时含 R3 与 R6，或 R5 与 R6，且没有 owner 退化声明。运行时：服务器已拒绝的三方分离事件计数（被拒次数本身就是预警） | 「审稿同时持有 R3 与 R6。它定标准的东西只能由 owner 验；建议把 R3 交给 owner 或再起一个角色。」 |

- **什么时候算**：静态检查在角色集声明时；运行时指标随协作报告（R13）每期算，服务实现后报告引用服务的数。
- **放哪**：一条事实 `project:allocation`；挖层「团队」一行只放一句摘要（「分配：2 条预警」）；详情在协作报告固定一节；声明时给 pm 的说明书里一段。
- **哪些切断是正当的**：独立审核那一刀（做的人不验、定判据的人不验）是三方分离要求的，不算无效移交；除此之外每一刀都要有承载上下文的产物，判断口径是「下一个角色能否只靠产物开工，不必再读、再问、再转述」。
- **负载陷阱的两张处方**：职责太杂就**拆**（把某项职责挪去别的角色或改成规则/服务）；职责包合理但活太多就**扩**（再起一个持有同一职责包的角色，backend-2 / frontend-2，任务按 claim 自然分流，指令仍发给具体角色）。拆错了会制造新的移交，扩错了会制造重叠；所以提示词必须先说成因再给处方。扩出来的角色是同一职责包的两个持有者，不算「重叠」——重叠指的是两个角色持有同一职责却没有分界；同包多角色的分界就是 claim。
- **不做**：不拒绝任何事件（三方分离除外）；不把「一人多职」一律当陷阱，最小团队本来就是一人多职，看流入与延迟，不看职责数；每种模式每期最多一条，带数字，防止预警变噪音（T10）。
